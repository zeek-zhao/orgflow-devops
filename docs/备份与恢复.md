# 备份与恢复

## 范围与前提

在仓库根目录执行；需要 Bash、Python 3、GNU tar/coreutils、`flock`、
Docker / Compose v2，以及访问目标 daemon 的权限。一次性容器使用 `alpine`，
演练前先确认镜像可用。Compose 项目名固定为 `orgflow-devops`：

| CLI / Compose 服务 | 备份与恢复的命名卷 | 内容 |
|---|---|---|
| `jenkins` | `orgflow-devops_jenkins_home` | Job、构建记录、插件、Jenkins 数据 |
| `nexus` | `orgflow-devops_nexus_data` | 仓库配置、数据库、制品 |
| `ldap` | `orgflow-devops_ldap_data` | LDAP 数据库 |

不备份镜像、容器可写层、日志、`out/Caddyfile`、工作区临时文件。
`caddy_data` 只存证书等可重建数据；`config/` 和服务配置在 Git 中。
`.env` 不在 Git 或本备份范围内，应通过受控的密钥保管流程另存，
恢复时使用匹配的配置和密钥，勿提交或在日志打印。
**LDAP 包只覆盖数据卷，不含 `ldap_config` 的 schema / cn=config。**
本手册演练保留原 `orgflow-devops_ldap_config`；全机丢失时必须另有同一停服时点的
该配置卷副本，或先重建与原库兼容的配置，不能把数据包当作完整 LDAP 灾备。
不要删除这两个 LDAP 卷，也不要在恢复期间重新执行初始化导入。

默认先停止正在运行的目标服务（最长优雅等待 120 秒），打包后再启回。
原来停止的服务不会因备份被启动。停服失败或停止后仍运行则拒绝备份。
`--no-stop` 仅用于已有外部一致性保障的维护场景，会警告，不能作为日常热备方案。
计划维护窗口；LDAP 停机会影响登录，Jenkins/Nexus 停机会中断任务和制品请求。
备份异常也会尝试启回原运行服务，重启失败必须人工处理。

## 命令速查

```bash
bash scripts/backup.sh --all
bash scripts/backup.sh --service ldap
bash scripts/backup.sh --service nexus --no-stop   # 仅逃生开关
bash scripts/backup.sh --verify out/backups/ldap-时间戳.tgz
make backup
make backup-verify BACKUP_FILE=out/backups/ldap-时间戳.tgz

# 非空卷必须 --force；dry-run 同样检查这一门槛
bash scripts/restore.sh --service ldap --file out/backups/ldap-时间戳.tgz --force --dry-run
bash scripts/restore.sh --service ldap --file out/backups/ldap-时间戳.tgz --force
make restore SERVICE=ldap BACKUP_FILE=out/backups/ldap-时间戳.tgz
# make restore 还必须在终端输入 YES；无显式参数或无确认则退出。
```

`BACKUP_DIR` 默认 `./out/backups`；可在调用时导出环境变量覆盖。
脚本不会 source `.env` 中的备份变量；Compose 自行读取 `.env`。
自定义环境文件使用 `ENV_FILE`；`COMPOSE` 的用法与 deploy 脚本相同。
示例：`BACKUP_DIR=/受控持久目录 BACKUP_RETENTION_DAYS=14 bash scripts/backup.sh --all`。
备份目录默认限制为仅当前用户访问；不要放在公开静态文件目录。

每次生成同一基名的三个文件，复制/异地保存时一起带走：

- `.tgz`：先写隐藏临时目录，`tar tzf` 完整列出成功后才发布；失败删除残包。
- `.sha256`：标准 `sha256sum` 的一行摘要和包文件名；重命名包需同步清单。
- `.meta`：`service`、`volume`、UTC `created_at`、压缩 `bytes`、
  `files`（tar 条目总数，含根目录、目录、链接）、`retention_days`。

校验和不代替来源认证；只恢复来自可信保管位置的包。校验/恢复允许读取
`BACKUP_DIR` 外存在的普通 `.tgz` 文件，但仍检查 checksum 和 tar；
旧包没有 `.sha256` 时会明确警告，只保证 tar 可读性。提供 `.meta` 时
恢复要求其服务和卷匹配；不 source 任何清单。恢复也会拒绝路径越界、
逃逸链接及设备等危险 tar 条目。`--verify` 不访问 Docker，不执行清理。

## Jenkins Job

`make jobs-test` 应渲染 `deploy-service`、`backup-service`、`restore-service` 三个 Job。
`restore-service` 参数为 `SERVICE`、`BACKUP_FILE`、`CONFIRM`：
**共享库仅接受 `CONFIRM=YES`，否则直接 `error()`，不进入 shell。**
`BACKUP_FILE` 留空时，在 `BACKUP_DIR` 的本服务 `.tgz` 中按 mtime 选最新包，
mtime 相同按文件名排序；最新包校验失败时终止，不静默回退其他包。
确认意味着允许 `--force` 覆盖，不绑定恢复凭据。

备份与恢复 Job 必须使用同一持久备份目录和同一 daemon；推荐给可信、专用
`orgflow-docker` agent 配置固定 `BACKUP_DIR`，不能依赖各 Job 不同的临时工作区。
同一备份目录中的服务级锁避免本脚本并发备份/恢复；它不能阻止其他人工写卷操作。
Jenkins 自身的维护优先从宿主机执行，避免停控制器中断 Pipeline 协调。
文件权限只能减少泄露风险；Jenkins/Nexus/LDAP 包均含敏感数据，需限制访问并异地保管。

## 恢复演练手册

1. 选择维护窗口，暂停外部写入。确认目标 daemon、Git 配置版本、原镜像版本、
   `.env` 与卷映射；`docker compose ps` 记录原健康状态。
   先记录业务基线：Jenkins 关键 Job/构建、Nexus 仓库列表、LDAP 条目数。
   用 `bash scripts/backup.sh --service ldap` 产生回退包并记录输出的准确路径。
   备份完成后服务会启回；检查三个产物均存在，妥善保留回退包。
2. 执行 `bash scripts/backup.sh --verify <包路径>`。
   再执行 `bash scripts/restore.sh --service ldap --file <包路径> --force --dry-run`，
   核对打印的服务、卷、包、现有条目数。dry-run 不停服、不修改数据卷。
3. 停服 → 恢复 → 起服由
   `bash scripts/restore.sh --service ldap --file <包路径> --force` 自动完成。
   脚本停服后再次检查非空门槛；用一次性 Alpine 清空卷内所有顶层条目
   （含隐藏文件）并保留卷本身，解包时保留归档权限/属主，然后 `compose start`。
   不使用 `docker volume rm`。任何解包失败都应保持停服、排查并重试完整恢复。
4. `docker compose ps ldap` 等待 **healthy**；若仍 starting，按健康检查间隔等待。
   超过五分钟或 unhealthy 时按下面失败处置，不把“命令返回成功”当作服务就绪。
   然后核对业务验证点，保存时间、包名、校验结果、恢复耗时、健康状态和条目数，
   不记录凭据或目录条目正文。其他服务按同样步骤分别演练，Jenkins/Nexus
   大库预留更长启动时间。

服务验证点：

| 服务 | 必须验证 |
|---|---|
| Jenkins | 容器 healthy；通过原入口正常登录；关键 Job、配置和构建记录存在 |
| Nexus | 容器 healthy；登录后仓库列表与基线一致；抽查已有制品可下载 |
| LDAP | 容器 healthy；有权限的目录查询成功，当前环境条目数仍为 **33**；登录链路可用 |

LDAP 验证命令使用容器现有环境中的密码，经 stdin 交给 ldapsearch，
不在命令参数中展开密码、不输出条目正文；域名按当前固定配置：

```bash
set -o pipefail
docker compose exec -T ldap sh -ec '
  printf "%s" "$LDAP_ADMIN_PASSWORD" |
    ldapsearch -x -LLL -H ldap://localhost:389 \
      -D cn=admin,dc=devops,dc=com -y /dev/stdin -b dc=devops,dc=com dn
' | grep -c '^dn:'
docker compose ps ldap
```

## 失败处置

| 情况 | 操作 |
|---|---|
| checksum 不符 / tar 损坏 | 不停服不解包；隔离坏包，重新从可信存储复制三个文件并校验，或选更早的已验证包。不能删除清单来绕过失败 |
| 卷不存在 / 被其他容器占用 | 检查 daemon 和固定项目名，用 `docker ps --filter volume=<卷名>` 找写入方；安排停服，不删卷。默认只停止映射服务，不会擅停其他容器 |
| 无法停服 | 退出，不执行带写备份/清卷；检查 Docker 权限、Compose 项目及停止日志，再重试 |
| 空间不足 / 备份失败 | 临时包清理，原运行服务尝试启回；检查磁盘、目录权限，修复后重新备份，不手工把 `.part` 当成有效包 |
| 清空或解包失败 | 服务保持停止。确认卷剩余空间、归档可读及权限，解决后从完整包重新 `--force` 恢复；不要直接启动半恢复数据 |
| 恢复后服务不起 | 本机检查 `docker compose logs --tail=100 <服务>`（日志可能含秘密，不直接分享）；核对镜像版本、属主/权限、磁盘、配置与数据版本兼容性，必要时再次停服并恢复回退包。LDAP 还要核对原 `ldap_config` |

## 保留策略与磁盘估算

`BACKUP_RETENTION_DAYS`（兼容脚本环境变量 `RETENTION`）为 0–99999 的整数，默认 7。
**0 只备份并警告“拒绝清理”**，不表示删除全部或保留零份。
成功完成本次备份后才清理所选服务的旧 `.tgz` 及同基名两个清单；
本次时间戳白名单始终排除，即使其 mtime 意外变旧也不删。
保留原 `find -mtime +N` 语义：按完整 24 小时向下取整后比较，
N=7 通常在满 8 天后才清理；不是精确到秒的七天截止线。不会清理其他服务。

每日每服务备份一次时，按至少 `(N + 2) × 每次压缩包大小总和` 估算本地保留空间，
另加一份最大服务包的临时空间、恢复解压所需卷空间和增长余量
（建议至少 20%）。Nexus 制品通常已压缩，不要假定能显著压缩。
频率增加需等比例增加磁盘预算；`RETENTION=0` 会无限增长，必须另有清理计划。
同磁盘备份不能抵御整机/磁盘故障，需将三件套异地保存并定期按本手册演练。

## ⚠️ verify-<svc> 会真的执行恢复

verify job 的三件套（部署→healthy→备份→断言，[#70](https://github.com/zeek-zhao/orgflow-devops/issues/70)）
包含**真实的备份→恢复演练**：跑 `verify-ldap` 会把 LDAP 数据回滚到当时最新的一份备份。
2026-11-06 实证：刚用 `ldapadd` 导入的新账号，在 `verify-ldap` 跑完后消失（被静默回滚到旧备份）。

**操作纪律：凡是改了 LDAP / Jenkins / Nexus 的业务数据，改完立即对相应服务重新备份**，
否则下一次 verify 就是静默回滚。


## 与 11 份服务文档、文档站的呼应

`docs/services/` 下 11 份服务文档都有「备份」段，逐服务写明**本服务落哪个卷、
`make backup` 是否覆盖、有什么缺口**：`jenkins` 只保 `jenkins_home`、`nexus` 只保
`orgflow-devops_nexus_data`、`ldap` 只保 `orgflow-devops_ldap_data`（**不含 `ldap_config`**）；
`caddy` / `router` / `dnsmasq` / `homepage` / `dex` / `oauth2-proxy` / `ldapadmin` /
`jenkins-agent` 无业务数据卷，配置在 Git 或 `.env` / `secrets/`，容器可重建。

服务文档的「备份」段是**入口指引**，卷口径、三件套、停服闸门、恢复步骤与失败处置
**以本文为准**；两处冲突时以本文为准。平台日常操作见 [使用说明](使用说明.md) §3。

文档经 [`scripts/gen_docs_site.py`](../scripts/gen_docs_site.py) 编成静态 HTML 后对外，
按最小披露排除含明文口令与内部派工的文档；本文与 11 份服务文档都属编入范围。
