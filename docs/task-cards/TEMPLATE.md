# 任务卡模板

> 一张卡 = 一次可派单的最小工作单元。**卡片正文就是派给执行方的 prompt**，
> 执行方读不到本仓库之外的任何上下文，所以卡片必须**自证**：读完就能开工，
> 不需要追问、不需要翻聊天记录。

## 三条硬规矩

1. **Issue 是需求真本，卡片是派单副本。** 两者冲突时以 Issue 为准，卡片只做引用不复述结论。
2. **验收条目必须是可执行命令 + 期望输出。** 写「功能正常」「体验良好」的条目一律作废。
3. **禁止事项要写具体。** 「不要乱改」没有约束力，「不得改 `tests/images.lock`」才有。

---

## 卡片骨架（复制以下全部内容到新文件）

````markdown
# [编号] 标题：一句话说清交付物

- **Issue**：#<编号>（需求真本）
- **分支**：`<type>/<issue>-<slug>`
- **依赖**：#<前置 Issue>（无则写「无」）
- **token 预算**：约 <N> 万 token；超预算先停下汇报，不要硬推

## 目标

一段话。**交付完成后，什么变了？** 不要写实现步骤，写终态。
读者应该能据此判断「做完了没有」。

## 背景与取证

只写执行方**无法自己查到**的事实：实测数据、环境限制、上游行为、踩过的坑。
每条都要带来源（命令 + 输出，或 Issue 链接）。**不要写猜测**——
写着「大概是因为」的段落会诱导执行方基于错误前提改代码。

| 事实 | 值 / 结论 | 怎么来的 |
|---|---|---|
| 例：`oauth2-proxy` v7.6.0 已无 LDAP provider | `--help` 里 `--ldap-*` 为 0 项 | `docker run --rm quay.io/... --help \| grep -c ldap` |

## 范围

逐文件列出。**改什么、新增什么、删什么**，一个文件一行。

**改**

| 文件 | 改法 |
|---|---|
| `path/to/file` | 具体到函数/字段级：删哪个变量、加哪个分支、改哪行断言 |

**新增**

| 文件 | 内容 |
|---|---|
| `path/to/new` | 这个文件要解决什么问题，含哪些关键内容 |

**删**

| 文件 | 理由 |
|---|---|
| `path/to/old` | 为什么留着有害 |

## 验收

每条都必须能**照抄执行**。给出命令和期望输出，不要给意图。

- [ ] `<命令>` → 期望 `<输出片段>`
- [ ] `<命令>` → 期望退出码 `0`
- [ ] 反证：`<故意破坏的动作>` → `<某用例>` 必须 **红**；恢复后复绿（贴两次输出）

**反证条目是必须的。** 只写「跑绿」的卡，无法区分「真的做对了」和「断言根本没生效」。

## 禁止事项

- 不得改 `<文件>`：<为什么>
- 不得把 `<凭据/token>` 写进 `<文件>`：<为什么>
- 不得为了过测试而放宽断言：断言是需求的一部分
- 不得自行合并 PR（合并由派单方做）

## 依赖与前置

执行方开工前必须成立的条件。任一不成立就**停下汇报**，不要自行绕过。

- [ ] `<命令>` 有输出 / 返回 `0`
- [ ] 需要人工动作：<例：在 GitHub UI 把某个包改成 public，无 API>

## 交付物

- [ ] 分支 `<分支名>`，提交信息符合 `docs/提交规范.md`
- [ ] PR 正文含：做了什么 / 关键决策与偏离 / 验收实测表 / 未验证项
- [ ] 验收输出贴进 PR 正文（命令 + 真实输出，不要转述）

## 交付后的记录

完成后由派单方补充，执行方不用填：

- PR：#
- 结果：<合并 commit / 遗留问题>
- 与本卡的偏离：<实际做法和卡不一致的地方，以及为什么>
````

## 为什么这么设计

| 字段 | 缺了会怎样 |
|---|---|
| 背景与取证 | 执行方重新踩一遍已知的坑，或者基于错误前提改代码 |
| 范围（逐文件） | 改动范围失控，评审时无法判断「该改的改了没有」 |
| 验收（命令 + 输出） | 交付物无法判断对错，只能靠感觉 |
| 反证 | 断言可能根本没生效，绿得毫无意义 |
| 禁止事项 | 顺手改了不该改的东西，且没人发现 |
| 依赖与前置 | 环境不满足时自行绕过，产出不可信的「成功」 |
| token 预算 | 在一条走不通的路上烧光预算，还不汇报 |

## 反例

下面这些写法会让卡片失去作用：

```markdown
## 目标
实现域名路由功能                          ← 无法判断做完没有

## 验收
- [ ] 功能正常                             ← 不可执行
- [ ] 代码质量良好                          ← 不可判断
- [ ] 测试通过                              ← 没说哪些测试、期望什么

## 禁止事项
- 不要乱改                                ← 没有约束力
```

```markdown
## 验收
- [ ] `make test-bats` 全绿                ← 缺反证，无法排除断言失效
```
