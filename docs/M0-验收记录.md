## 四、执行前必须解决的技术障碍（DooD 三件套）

wfbox 用 DooD，`docker compose` 里的 bind mount 由 **213 的 daemon** 解析，不是容器内路径。所以：

| 障碍 | 现象 | 解法 |
|---|---|---|
| **① bind mount 路径** | `- ./out:/etc/caddy:ro` 会被解析成 213 宿主上的 `/home/jenkins/workbuddy/orgflow-devops/out`，而容器里的 repo 在别处 → 挂空目录 | 把仓库以**完全相同的绝对路径**挂进 wfbox：`-v /home/jenkins/workbuddy/orgflow-devops:/home/jenkins/workbuddy/orgflow-devops` |
| **② uid 不匹配** | 镜像内 `dev` uid=1000，213 上 jenkins uid=**2000**；`.env` 是 `0600 jenkins:jenkins` → 容器内读不到 | `docker exec -u root wfbox usermod -u 2000 dev && groupmod -g 2000 dev`，重启容器 |
| **③ 镜像名** | 213 上只有 `ghcr.io/zeek-zhao/wfbox:24.04`，compose 要 `wfbox:24.04`；且 213 **Docker Hub 不通**，不能本地 build | `docker tag ghcr.io/zeek-zhao/wfbox:24.04 wfbox:24.04`，然后 `up -d`（不带 `--build`） |

> 另注：213 的 Docker 是 **26.1.0**，wfbox 内 CLI 是 28.4.0，API 版本协商可用，无需处理。

**另外两条环境事实**：

- Windows → 213 **:2222 被主机防火墙拦**（:22 通），所以进 wfbox 用
  `docker exec -u dev wfbox bash -lc '...'`，不走 SSH。`sudo` 需密码，读不到 iptables 规则。
- wfbox 必须把仓库挂到**与宿主完全相同的绝对路径**，否则 DooD 下 compose 的相对 bind（`./out`）会挂空。

### 10.3 两个硬事实（推翻了「不引插件」的初选）

**① Jenkins 里一个插件都没有。** `/var/jenkins_home/plugins/` 是空的：

```
ssh-slaves: no        configuration-as-code: no     git: no
workflow-aggregator: no                            credentials: no
```

所以 `securityRealm=None` 不是「JCasC 没生效」，是**插件压根没装**。连带后果：
`make jobs` 推的 `deploy-service` / `backup-service` / `restore-service` 是 pipeline job，
**没有 workflow-aggregator 跑不起来**；没有 `git` 拉不了仓库；没有 `ssh-slaves` 连不上 agent。

**② `node('orgflow-docker')` 没有对应节点。** Jenkins 只有 Built-In Node（label `built-in`），
容器内 `which docker` → 无、`/var/run/docker.sock` → 无。
→ 那三个 job **从建起来就没跑通过**，一直 pending。这是 M0 里一个此前没被发现的缺陷。

### 10.4 HomePage 报错：根因与修法

现象：`https://home.<domain>/` → `Something went wrong. TypeError: Failed to construct 'URL': Invalid URL`。

**根因**：`config/homepage/bookmarks.yaml` 把书签值写成了**映射**，homepage 要求**列表**：

```yaml
# 现在（错）—— href/icon 被解析器丢弃
- 官方文档:
    - Caddy:
        href: https://caddyserver.com/docs/
        icon: mdi-web

# 应该（对）
- 官方文档:
    - Caddy:
        - abbr: CD
          href: https://caddyserver.com/docs/
```

**证据**：`GET /api/bookmarks` 返回的 5 个书签**只有 `name`，没有 `href`**。
前端源码 `let a = e.description ?? new URL(e.href).hostname` 拿到 `undefined` → 抛错。
服务端渲染正常（curl 200，HTML 里 href 都在），所以**只有真浏览器会炸**。

5 个书签全中。修法：改成列表形式；防回归：`/api/bookmarks` 断言每个书签必须有 `href`。

**踩的 4 个坑（全部有 CI 现场）**

| 现象 | 根因 | 正解 |
|---|---|---|
| `找不到 orgflow 网络` | compose 里 `networks.orgflow.name: orgflow` **显式命名**，不是默认的 `<project>_orgflow`；脚本却按默认规则 `grep '_orgflow$'` 去猜 | 照抄 compose 的显式名。**猜命名规则本身就是错的** |
| `change-password` 返回 **415** | 该端点声明的是 **text/plain**，body 就是新密码本身，不是 JSON | `-H 'Content-Type: text/plain' --data-binary "$PASSWORD"` |
| 回退 `PUT /security/users/{id}` 返回 **400** | 那条路要求带完整用户对象（firstName/lastName/email/status/source），缺一个就报 | 这条路本来就走不通，删掉，不要「盲回退」 |
| of-nexus 解析断言以**状态码 2** 失败 | 在容器里跑 `sh -c 'if command -v getent…'`，nexus 底座镜像精简，探测脚本本身跑不起来 | 从宿主侧逐个试 `getent → nslookup → dig → curl`，缺哪个都只是非 0，`\|\| true` 吞掉 |

另外两条与 nexus 无关但同批修掉的：

- **`curl` 的 `%{remote_ip}` 只在连接建立后才填**，所以降级探测不能打一个没人监听的端口
  （连接被拒 → 空串 → 和「解析失败」同一个现象）。改打网关 80。
- **`docker run` 不会把容器名变成网络别名**（compose 会），必须显式 `--network-alias nexus`；
  同理要显式 `--dns 172.31.0.2`，否则退回 Docker 内嵌 DNS，解析不了 `*.<domain>`。

## 十二、验收过程暴露的缺陷（核心复盘）

> 三个真机缺陷 + 三个脚本缺陷，全是「机器全绿、文档自洽、一上真机就挂」的典型。
> 共同点：**报错文案指向的地方全都不是真因**。
> 所以判据不能只看 healthy，必须有一条真正打穿链路的动作。

### 12.1 缺陷 1：agent 驱动不了宿主 docker（PR #55，`aad6881`）

| 项 | 内容 |
|---|---|
| 症状 | job 报 `找不到网络 orgflow；先跑 make deploy`，而网络明明在 |
| 伪装 | `docker network inspect` 的 permission denied 被脚本吞成了「网络不存在」 |
| 真因 | 上游 `jenkins/ssh-agent` 镜像 `PermitRootLogin no` → job 以 **jenkins(1000)** 跑，不在 socket 的组里；`/var/run/docker.sock` 是 `root:<docker 组> 0660` |
| 为什么不能按组名 | 容器内 `/etc/group` 与宿主对不上（213 宿主同 gid 998 叫 `docker`，容器内叫 `systemd-network`）→ 只能用数字 gid |
| 修法 | compose `group_add: ${DOCKER_GID:-0}`；deploy.sh / harness / Makefile 三处 `stat -c %g` 探测并 export |

### 12.2 缺陷 2：agent 的 sshd host key 不固定（PR #56，`3fde1ef`）

| 项 | 内容 |
|---|---|
| 症状 | job 卡 `'orgflow-docker' is offline`；agent 日志只有 `Connection closed ... [preauth]` |
| 伪装 | 页面上等一个「Trust SSH Host Key」的点击，没人会去点；三个 pipeline job 全部 pending |
| 真因 | 原策略 `manuallyTrustedKeyVerificationStrategy` 记的是**第一次见到的 key**；而 agent 容器 `/etc/ssh` 不持久化，重建时 `ssh-keygen -A` 换新 key → 立刻不匹配 |
| 修法 | host key 做成受管产物：`gen-agent-key.sh` 幂等生成 `secrets/agent_host_key`，compose 挂到 `/etc/ssh/ssh_host_ed25519_key:ro`（`ssh-keygen -A` 见到已存在就跳过 ed25519），JCasC 改 `manuallyProvidedKeyVerificationStrategy` 显式声明 |
| 空值风险 | 该策略**构造时就 parseKey**，空串会让 JCasC 整份配置应用失败（Jenkins 起不来）→ 三处入口都导出并拦空值 |
| 格式坑 | `.pub` 第三列是注释，必须切成「算法 base64」两列，否则 parseKey 失败 |

**验证记录（真机）**

- 挂载方案可行性：`ssh-keygen: generating new host keys: RSA ECDSA` —— 跳过了 ED25519，
  指纹来自 `secrets/agent_host_key.pub`
- 插件侧确认：`ssh-slaves 3.1097.v868116049892`，内层 `WEB-INF/lib/ssh-slaves.jar` 里
  `hudson/plugins/sshslaves/verifiers/ManuallyProvidedKeyVerificationStrategy.class` 存在，
  `config.jelly` 里字段名是 `key`
- **注意**：外层 `.jpi` 里 grep 不到这个类 —— 它在嵌套 jar 里，压缩后不可见。
  直接 grep 外层会得出「插件不支持」的错误结论。

### 12.3 缺陷 3：`group_add` 到不了 SSH 会话（PR #57，`331fe730`）

**这是三个里最隐蔽的一个。**

| 项 | 内容 |
|---|---|
| 症状 | 缺陷 1「修好」之后，job 仍然报 `找不到网络 orgflow` |
| 伪装 | deploy.sh 的端到端检查 `docker exec -u jenkins ... docker info` **一路绿灯** |
| 真因 | `docker exec` 会继承容器 OCI spec 的 `AdditionalGids`（= `group_add` 的效果）；而 sshd 给登录会话调 `initgroups()`，**按 `/etc/group` 重置**附加组。同一容器里：`exec` 是 `groups=1000,998`，`su`/`ssh` 只有 `1000` |
| 判据教训 | 用 `docker exec -u` 做端到端检查是**假阳性**，等于没有判据。必须用 `su -s /bin/sh -c '...' jenkins`（和 sshd 一样走 initgroups） |
| 修法 | `agent-entrypoint.sh` 在 `exec setup-sshd` 前把 `DOCKER_GID` 写进 `/etc/group` 并 `usermod -aG docker jenkins`；compose 把 `DOCKER_GID` 透传给 agent；deploy.sh 的检查改走 `su`，并加反向断言禁止改回 `docker exec -u` |

**真机证据链（可复现）**

```sh
docker exec of-jenkins-agent su -s /bin/sh -c 'id' jenkins   # 改之前：groups=1000
docker exec of-jenkins-agent getent group docker             # 改之后：docker:x:998:jenkins
docker exec of-jenkins-agent su -s /bin/sh -c 'docker info --format {{.ServerVersion}}' jenkins  # 26.1.0
```

**一条经验**

> 「容器 healthy + 节点 online」证明不了 job 能跑。
> 真正的验收动作必须是**一次打穿全链路的真实 job**（nexus-deploy），
> 而且要在**重建容器之后**再跑一遍 —— 这三个缺陷都是重建后才现形的。

### 12.5 脚本自身的三个缺陷（PR #59，`51d92db3`）

> 这一段是「验收脚本自己挡住了验收」。三个缺陷都在 Windows PS 5.1
> （`5.1.26100`，Windows 11）上实测复现，PS 7 上不一定复现。

| # | 症状 | 真因 | 修法 |
|---|---|---|---|
| 1 | `New-Object System.Net.Http.HttpClientHandler` 报「找不到类型」 | PS 5.1 默认**不加载** `System.Net.Http` 程序集 | 干脆不用 HttpClient |
| 2 | 补上 `Add-Type` 后抛「此线程中没有可用于运行脚本的运行空间」 | ScriptBlock 赋给 `ServerCertificateCustomValidationCallback` 后，回调跑在**线程池线程**上，没有 runspace | 证书信息改用 `SslStream`（`AuthenticateAsClient` 里同步同线程调回调） |
| 3 | dex 永远红：`状态码 404，期望 302` | dex 没有根 handler，`/` 本来就是 404 | 判据改成 `/dex/healthz` = 200，加 `$ProbePaths` 表 |

**第 2 条最坑**：脚本自己把异常包装成「证书校验失败（）——根证书没导入？」，
括号里是空的（回调根本没跑），但人会顺着「根证书」方向查很久。
**报错文案指向哪里，不代表真因在哪里。**

**修完的实测输出**

```
== 1. hosts ==        6 条记录齐全
== 2. 根证书 ==       CN=Caddy Local Authority - 2026 ECC Root
== 3. 站点 ==
  [OK] jenkins   302  [OK] nexus   200  [OK] ldapadmin 302
  [OK] dex       200  [OK] auth    302  [OK] home      200
验收全部通过。  EXITCODE=0
```

**测试**：`WinAcceptanceScriptTests` 3 条 —— 禁止 `HttpClient` 自定义回调、
dex 必须打 `/dex/healthz`、`.ps1` 必须 UTF-8 BOM + CRLF。

**过程中的一次事故**：`git checkout -f -B <新分支> origin/main` 把未提交的改动
一起冲掉了（`-f` 强制丢弃工作区）。正确顺序是**先建分支、再改文件**，或者先 `git stash`。
