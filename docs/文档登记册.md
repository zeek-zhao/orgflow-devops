# 文档登记册

> 配置项清单（IEEE 828 §配置标识 / §状态纪实）。**这是文档体系的唯一权威清单**：
> 一篇文章在不在这里、什么状态、谁负责、什么时候该重看，全看这张表。
> 规则见 [文档规范](engineering/文档规范.md)，阅读入口见 [文档地图](文档地图.md)。
>
> 门禁：`python3 scripts/check_docs_meta.py`（`make docs-check`）。它硬查五件事 ——
> 磁盘与登记册双向一致、DOC-ID 唯一且合规、`approved` 必须有评审日期、
> `superseded` 必须指向替代者；复审超期只报 WARN，不阻断。

## 列的含义

| 列 | 含义 |
|---|---|
| `DOC-ID` | 永久编号，永不复用。改文件名不改编号 |
| `层级` | 入口 / 规程 / 参考 / 记录，判定见规范 §2 |
| `状态` | draft / review / approved / superseded / archived，含义见规范 §4 |
| `评审日期` | **该文档内容最后一次被接受的日期**。本表初建时取「该文件最后一次内容提交日期」，不臆造审批 |
| `复审(月)` | 到期只提示、不阻断；到期后由负责人决定续期 / 改写 / 退役 |
| `关联` | Issue 号，用于需求→设计的追溯 |

## 统计

统计口径是**表中实际登记的行数**，不是历史累计。上一版写「合计 58 / 记录 30」，那是双仓导出时代的旧账，
单仓化剔掉内部记录文档后没有同步 —— 表里 21 行却宣称 58 篇。这种数字比没有统计更糟，
因为它会被当成「文档很齐全」的证据。2026-11-14 文档 ISO 化重组：并入 3 篇旧文档（工程开发说明、M0镜像与CI、WBS与里程碑），新增 5 个目录索引（各子目录 README），表中 41 行，统计段同步为 41。

| 层级 | 篇数 | DOC-ID 段位 |
|---|---|---|
| 入口 | 8 | E-001 ~ E-008 |
| 规程 | 13 | P-001 / P-006 ~ P-009 / P-011 ~ P-018 |
| 参考 | 20 | R-001 / R-002 / R-004 ~ R-008 / R-010 ~ R-021 / ADR-13 |
| 记录 | 0 | 按最小披露全部移出仓库，见下节 |
| **合计** | **41** | |

全部文档按五层子目录存放：`docs/project/`（项目治理）、`docs/engineering/`（工程规程）、
`docs/services/`（服务手册）、`docs/records/`（决策与归档）、`docs/network/`（网络架构），
每个子目录有 README 索引。子目录不豁免登记 ——
`scripts/check_docs_meta.py` 递归查 `docs/**/*.md`，路径必须按 `docs/project/xxx.md` 原样写进本表。

## 记录层（DOC-L-*）为什么是 0 篇

规范 §2 保留了「记录」这一层，但**当前仓库里没有任何记录层文档**：会话交接、待办、验收记录、
任务卡全部按最小披露移出。这不是漏登记，是有意为之。

后果要写清楚，别假装没有：

- 任务卡**只存在于 GitHub Issue**，仓库内没有实体（见 [文档规范](engineering/文档规范.md) §7）；
- 「某次验证的过程」在仓库里查不到，只剩结论；
- DOC-ID 的 `TC-` 例外在规范 §3 保留，但当前没有使用者。
