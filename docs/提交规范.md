> 该邮箱是 GitHub 账号 `zeek-zhao` 的 primary 且已验证邮箱，因此归因不受影响。

## 1. 规则

| 对象 | 约束 | 强制手段 |
|---|---|---|
| author | 恒为 `zeek.zhao <zeek.zhao@foxmail.com>` | pre-commit + pre-push + CI |
| committer（分支） | 同上 | pre-commit + pre-push + CI |
| committer（main） | 允许 `GitHub <noreply@github.com>` | 不约束 |

**为什么 main 上放宽 committer**：GitHub 的 squash 合并由平台生成提交，committer 恒为
`GitHub <noreply@github.com>`，这不是配置能改的。若强行要求 main 上 committer 也是本人，
就只能放弃 GitHub 合并、改成本地 `git merge --squash` 后直推主干——那会破坏「禁止直推主干」
这条更重要的约束。两害相权，author 严格 + 分支 committer 严格，main 承认平台事实。

### 平台产物：不参与身份校验

GitHub 会生成三类提交，它们不是人写的，校验时必须排除（`--no-merges`）：

| 提交 | author | committer | 何时出现 |
|---|---|---|---|
| PR 合成合并提交 | `zeek-zhao <42319166+zeek-zhao@users.noreply.github.com>` | `GitHub <noreply@github.com>` | `refs/pull/<n>/merge`，CI 默认检出的就是它 |
| Squash 合并提交 | **账号 noreply 邮箱** | `GitHub <noreply@github.com>` | 点「Squash and merge」后落到 main |
| Rebase 合并后的提交 | **保留原始 author（本人）** | 账号 noreply 邮箱 | 点「Rebase and merge」后落到 main |

实测取证（PR #20）：

```
sha   : 3c1c9d43da
author: zeek-zhao <42319166+zeek-zhao@users.noreply.github.com>
commit: GitHub <noreply@github.com>
parents: ['f42803d7', '6faac26c']
```

所以 `make identity-check` 与 `identity.yml` 都用 `--no-merges` 过滤，
只对真人提交做校验。**如果把 `--no-merges` 去掉，PR 上的 CI 会永远红。**

另外注意：CI 检出必须是**全量**（`fetch-depth: 0`）。浅克隆下合并提交会被
git 当成"无父提交"，`--no-merges` 就过滤不掉它——这条已实测踩过。

### 合并方式：必须用 Rebase，禁止 Squash

**Squash 会把 author 改写成账号 noreply 邮箱**，等于每次合并都把错误身份写进主干。
Rebase 保留原始 author，只把 committer 交给平台，而 committer 在主干上本来就允许。

`wf4.sh merge` 的默认值已改为 `rebase`（ai-workflow 仓库）。用网页合并时请选
**「Rebase and merge」**，不要点「Squash and merge」。

**这条不是纸面规矩，是踩过的。** 2026-10-31 合 PR #25 时用了 `squash`（走 REST API
`merge_method=squash`，等价于点「Squash and merge」），结果：

```
$ make identity-check
✗ author 异常: 42319166+zeek-zhao@users.noreply.github.com
```

**为什么 `--no-merges` 没兜住**：那条过滤的前提是「GitHub 生成的提交都是合并提交」。
但 squash 提交**只有一个父提交**，`--no-merges` 根本不会过滤它。而 rebase 合并
**不产生新提交**，所以之前 20 多次合并从没暴露这个缺口。

更要紧的是：squash 提交和 rebase 后的提交在脚本层面**无法区分**——都是「单父 +
committer 是 noreply」。所以这个缺口没法用脚本补，只能靠流程约束。
CI 会红，红得很难看（全历史扫描，一次一条），这就是它存在的意义。

## 2. 三层防护

```
① 仓库配置     git config user.name / user.email     ← 最容易被 214 的全局身份覆盖
② 本地钩子     .githooks/pre-commit / pre-push        ← 提交时即拦，错误进不了历史
③ CI 门禁      .github/workflows/identity.yml         ← 换机器、换 agent 也逃不掉
```

装钩子：

```bash
make hooks          # 等价于 git config core.hooksPath .githooks && chmod +x .githooks/*
```

> 钩子不随克隆自动生效（`core.hooksPath` 是本地配置），所以 CI 那层不能省。

## 3. 出错了怎么修

**还没提交**（只是配置错了）：

```bash
git config user.name  "zeek.zhao"
git config user.email "zeek.zhao@foxmail.com"
```

**已提交但没推**：

```bash
git commit --amend --reset-author --no-edit
```

**已推送、还没合并**（只能改自己分支，别动主干）：

```bash
git rebase -i origin/main --exec 'git commit --amend --reset-author --no-edit'
git push --force-with-lease
```

**已合并进 main**：需要重写历史，见下节。这是最后手段，先确认没有别人基于旧提交在干活。

## 6. 提交消息规范

提交消息只回答两个问题：**改了什么、为什么改**。不允许出现作者署名类信息。

### 禁止的两类内容

| 类型 | 例子 | 为什么禁 |
|---|---|---|
| 协作者尾注 | `Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>` | 一条提交出现两个作者，直接违反"提交人唯一" |
| AI 生成署名 | `🤖 Generated with Copilot`、`Generated by Claude Code` | 提交历史是审计证据，不该记录工具 |

被拦的关键词（不区分大小写）：`copilot` `claude` `chatgpt` `gpt-4/5` `gemini`
`cursor` `codex` `codeium` `windsurf` `tabnine` `aider` `openai` `anthropic`。

> 注意：**主语里合法提到工具名不算违规**。例如
> `feat(wf3): copilot 每次任务记录 token 用量` 是描述功能，不是署名，不会被拦。
> 拦截的是"生成/协助"语义的署名，不是关键词本身。

### 三层拦截

| 层 | 位置 | 时机 |
|---|---|---|
| 本地钩子 | `.githooks/commit-msg` | `git commit` 时 |
| CI 门禁 | `.github/workflows/identity.yml` | PR 与 main 推送时 |
| 派单约束 | ai-workflow `wf3` 任务卡模板 | 派任务给 AI 时就声明 |
