# 升级与回滚

> 状态：适用 | 最后核对：2026-11-24 | 对应分支：feat/m0-release（R8）

M0 的升级粒度是**单服务**，纪律是「不重启整机、不重建网络/数据卷」。单服务重建约 1~2 秒中断，避开使用时段。

## 1. `up.sh` 的三种启动模式

| 命令 | 行为 | 适用场景 |
|---|---|---|
| `bash up.sh --only <svc>` | 存在且 healthy 就跳过（零停机）；不健康才 `up -d` | 日常幂等启动 |
| `bash up.sh --recreate <svc>` | 打印回滚命令 + 5 秒确认窗，按指纹变更决定是否 `up -d --force-recreate` | 配置指纹变更后的安全重建 |
| `FP_STRICT=1 bash up.sh` | 指纹 stale 时自动 force-recreate | 严谨环境，接受短中断 |
| `bash up.sh` | 按 manifest 顺序逐服务启动，失败即停 | 全栈起 |

> **已知注意点**：`--recreate` 的 force-recreate 依赖 `org.of.fp` 指纹变化。若只改了 bind mount 的配置内容（如 homepage 的 `services.yaml`）而镜像/网络/卷未变，指纹可能不变，`--recreate` 会走普通 `up -d` 而不换容器——此时 HomePage 进程仍缓存旧配置。遇到这种情况用等价的 compose 命令强制重建单容器（见 §3）。

## 2. 标准升级流程

1. **改代码/配置**：在 `feat/m0-release` 拉工作分支，一任务一 Issue 一 PR，合入主线。
2. **本地同步**：`git checkout feat/m0-release && git pull`。
3. **静态门禁**：`make check && make test && python3 scripts/render-homepage.py --check`。
4. **确定升级目标**：
   ```bash
   bash up.sh --dry-run            # 看实际解析的镜像与顺序（不启动）
   docker inspect -f '{{.Image}}' of-<svc>   # 记录当前镜像 digest（回滚用）
   ```
5. **单服务升级**：
   ```bash
   bash up.sh --recreate <svc>
   ```
   若是指纹未变的配置改动（如 HomePage 卡片），改用 §3 的 compose 强制重建。
6. **健康确认**：`bash status.sh` + `curl` 对应健康端点。
7. **刷新配额证据（构建链路必做）**：涉及 builder/jenkins-agent 或要推 change 时，重建后刷新证据并确认新鲜度：
   ```bash
   bash up.sh --recreate builder          # 两段式：启动前预检 + 启动后取证（见《构建资源配额》§3）
   make quota-guard                        # 或手动刷新（container 默认 of-builder）
   make quota-status                       # 必须 0：age≤10min；非 0 则推 change 必被 Quota gate 拦
   ```
8. **记录**：命令 + 退出码 + 关键输出到 `docs/records/执行日志/<日期>.md`。

> **刷新机制安装（m2.5.3 P0-1）**：若部署机尚未安装自动刷新，按 PID1 择一安装（详见《构建资源配额》§4）：systemd 主机 `make quota-install`；cron 可用 `make quota-cron-install`（用户 crontab 5 字段 / `/etc/cron.d` 6 字段）；PID1=supervisord `make quota-supervisor-install`；runit `make quota-runit-install`；均不可用才 `make quota-daemon-install`（执行日志写明理由）。安装前先 `make quota-cleanup-nohup` 精确清旧进程、禁止双写；安装后 `make quota-status` 确认 `mechanism=` 与进程一致，并 `kill -9 $(cat artifacts/quota/daemon.pid)` 验证 ≤60s 自愈拉起。

> **顺序纪律（m2.5.1 P2-3）**：部署必须遵循 **`git pull` → `make check` → `up.sh --recreate/--pull` → `make quota-guard` → 再推代码**。自检报告的 `commit` 取自 controller 只读挂载的 `/opt/orgflow/repo`，若未先 `git pull` 就 reload/重启，报告 commit 会永远落后一版；**报告 `commit` 必须等于当前部署头**（`git rev-parse --short HEAD`），不等即视为部署未完成，禁止进入评审/推 change。真机还需确认 `make quota-status` 为 0 后再推，否则 change 会在 Quota gate 被自锁拦截。

## 3. 强制重建单容器（指纹未变时的等价操作）

以 homepage 为例（其余服务同理，改服务名与 compose 路径）：

```bash
# 先记录旧镜像与 project（回滚用）
docker inspect -f '{{.Image}}' of-homepage
# project 必须与线上存量一致（默认 orgflow-minimal），否则 container_name 归属不符会静默失败
COMPOSE_PROJECT=orgflow-minimal docker compose \
  --env-file config/defaults.env \
  -p orgflow-minimal -f services/homepage/compose.yml \
  up -d --no-deps --force-recreate homepage
# 等健康
until [ "$(docker inspect -f '{{.State.Health.Status}}' of-homepage)" = healthy ]; do sleep 2; done
```

> `up -d --no-deps --force-recreate` 只重建目标容器，不动其它容器、网络与卷。出现 orphan 容器警告是正常的（其它服务不在本 compose 文件里），**不要加 `--remove-orphans`**，否则会误删其它服务容器。

## 4. 镜像 tag / digest 变更

- 默认模式（`USE_LOCAL_IMAGES=0`）：镜像由 `services/<svc>/compose.yml` 的 `image:` 字面 `@sha256` digest 固定，来源 `config/images.lock`；升级 digest 需改 compose + lock 并过 `scripts/check-images.sh`。
- 本地模式（`USE_LOCAL_IMAGES=1`）：镜像取 `config/images.env` 的 `IMAGE_<SVC>`，须 lock 无 PENDING 且本地镜像存在，否则自动回退 GHCR。详见 [镜像与供应链](镜像与供应链.md)。
- 变更 digest 后按 §2 重建对应服务即可，其它服务不受影响。

## 5. 回滚

`up.sh --recreate` 启动时已打印回滚命令（含旧镜像 ID）。回滚两条路径：

### 5.1 代码/配置回滚（推荐）

```bash
git revert <出错的 commit>              # 或 git reset 到上一个已知良好 commit（不 force push 已推送历史）
git checkout feat/m0-release && git pull
bash up.sh --recreate <svc>             # 或 §3 的 compose 强制重建
```

### 5.2 镜像回滚

```bash
# 用升级前记录的旧 digest
docker rm -f of-<svc>
COMPOSE_PROJECT=orgflow-minimal docker compose \
  --env-file config/defaults.env -p orgflow-minimal \
  -f services/<svc>/compose.yml up -d --no-deps <svc>
# 或临时覆盖镜像 tag
IMAGE_<SVC>=<旧digest> bash up.sh --recreate <svc>
```

### 5.3 数据回滚

若升级涉及数据变更（如 LDAP 配置），按 [备份与恢复](备份与恢复.md) 从快照恢复卷后重建对应服务。**回滚数据卷前先停对应容器，避免写入中恢复。**

## 6. 升级失败判定

- `bash status.sh` 有非 healthy 服务 → 立即按 §5 回滚，不留故障过夜。
- `/status` 页面红卡 → 看对应服务 `docker logs of-<svc> --tail 100`，按 [排障](排障.md) 定位。
- 健康检查通过但页面内容旧（HomePage 缓存）→ 按 §3 强制重建容器。
