> **口径统一（r5 §2.4）**：`upstreamDigest` 列现在对所有行统一记「Dockerfile `FROM` 的基底 digest」。此前 dnsmasq/router/certs-init 记的是自建产物的 manifest digest（`9f1a…`/`e5fd…`），与 caddy/ldap/homepage 记基底的口径冲突（同列两义），已纠正为 `ubuntu:24.04@sha256:fe815609…`。
> **M1 标识为何不用 imageId**：构建产物的 imageId/manifest digest 每次构建随机变化，把它回填进 compose 会形成「配置领先镜像」的死循环。改用内容哈希后：构建输入（Dockerfile + 它 COPY 的真源文件）不变 → 哈希恒定；输入一变 → 哈希与 tag 必变，由 `make check`（`--mode=lock`）拦截漂移。

## 3.5 两种运行模式（T10）

| 模式 | 开关 | 注入的 env-file | compose 选中的 image | 适用场景 |
|---|---|---|---|---|
| **默认 GHCR ctx tag**（线上） | `USE_LOCAL_IMAGES=0`（默认） | 仅 `config/defaults.env` | `${IMAGE_*:-<GHCR>:ctx-<12>}`（M1）/ `${IMAGE_*:-<GHCR>@sha256:...}`（M0），`pull_policy: missing/never` | 线上零停机；不依赖本地是否构建过 |
| **本地自建** | `USE_LOCAL_IMAGES=1` | defaults + `config/images.env`（后者覆盖） | `orgflow/m0-*:v2` / `orgflow/m1-*:ctx-<12>`（须 lock 校验通过且镜像存在） | 改了源码/配置后本地验证 |

- 本地模式前置校验：`up.sh` 先跑 `scripts/check-images.sh --mode=lock`（tag 一致 + M1 内容哈希强校验），再核对目标镜像 `docker image inspect <tag>` 存在；任一不满足 → **告警并回退默认 GHCR**，绝不静默指向不存在的 tag。
- `config/images.env` 只在 `USE_LOCAL_IMAGES=1` 时注入；**不得**把 `orgflow/m0-*` 写进 `defaults.env`（那会让默认路径依赖本地构建状态）。
- 配置指纹 `org.of.fp` 已纳入 `config/images.env` 与 `USE_LOCAL_IMAGES`，切模式后指纹变化可见。

## 4. 升级流程（r5 §2：内容 tag，无回填步骤）

1. 改动某服务源码或配置（如 `services/jenkins/plugins.txt`）→ `bash scripts/sync-build-context.sh` 同步构建上下文。
2. `make images-hash` 计算 M1 内容哈希；把新的 64hex 前 12 位写入 `tests/images.lock` 的 tag 后缀与 contextSha256，并同步两个 jenkins compose 的 `ctx-<12>` 默认值。
3. CI（`.github/workflows/build-images.yml`）按内容 tag 构建推 GHCR：r5 已删除旧的 imageId 回填 job 与 PR 回填步骤，构建产物不再回写 lock/compose。
4. `bash scripts/check-images.sh --mode=lock` + `make check` 全绿后合并。反向门禁保证：故意改 Dockerfile 而不更新 lock → `make check` 立即变红。

## 5. 允许删分支（AC-20）

删除 main 之外的任何分支后，本分支仍能独立 `build → push → deploy`：
