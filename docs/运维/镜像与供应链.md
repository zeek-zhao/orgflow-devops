## 3.5 两种运行模式（T10）

| 模式 | 开关 | 注入的 env-file | compose 选中的 image | 适用场景 |
|---|---|---|---|---|
| **默认 GHCR digest**（线上） | `USE_LOCAL_IMAGES=0`（默认） | 仅 `config/defaults.env` | `${IMAGE_*:-<GHCR>@sha256:...}` 回退已验证 GHCR 代理镜像，`pull_policy: never` | 线上零停机；不依赖本地是否构建过 |
| **本地自建** | `USE_LOCAL_IMAGES=1` | defaults + `config/images.env`（后者覆盖） | `orgflow/m0-*:v2`（须 lock 校验通过且镜像存在） | 改了源码/配置后本地验证 |

- 本地模式前置校验：`up.sh` 先跑 `scripts/check-images.sh --mode=lock`，再核对目标镜像的 lock imageId 非 `PENDING-BUILD` 且 `docker image inspect <tag>` 存在；任一不满足 → **告警并回退默认 GHCR**，绝不静默指向不存在的 tag。
- `config/images.env` 只在 `USE_LOCAL_IMAGES=1` 时注入；**不得**把 `orgflow/m0-*` 写进 `defaults.env`（那会让默认路径依赖本地构建状态）。
- **PENDING-BUILD 处置**：若 `tests/images.lock` 某行 imageId=`PENDING-BUILD`（历史上 homepage/ldapadmin 因沙箱 vfs 磁盘限制），该服务不能启用本地模式、自动回退 GHCR；须在 overlay2 + 充足磁盘的 runner 上构建后由 PR 回填真实 imageId（T11 已完成，见 PR #237）。当前 lock 已零 PENDING。
- 配置指纹 `org.of.fp` 已纳入 `config/images.env` 与 `USE_LOCAL_IMAGES`，切模式后指纹变化可见。

## 4. 回填流程（升级 / 首次构建）

1. 改动某个服务源码或配置 → `bash scripts/sync-build-context.sh` 同步构建上下文。
2. 本地或 CI 构建镜像 → `scripts/build-images.sh`（输出真实 `docker image inspect {{.Id}}`）。
3. `make images-lock` 回填 `tests/images.lock` 的 imageId 与上下文快照（不手填哈希）。
4. PENDING-BUILD 项（如出现）：在 GitHub 手动触发 `workflow_dispatch`（services=homepage,ldapadmin），`fill-pending` job 在 overlay2 runner 构建后**以 PR 回填**，不直接 push（T11 已用此流程回填 homepage/ldapadmin，PR #237）。
   > 若仓库未开启「Allow GitHub Actions to create and approve pull requests」，fill-pending 会在建 PR 步骤失败，但回填分支已推送；维护者可用 PAT 基于该分支手动开 PR。
5. `bash scripts/check-images.sh --mode=lock` 零 PENDING + `make check-all` 全绿后合并。
