# 备份与恢复

> 状态：适用 | 最后核对：2026-11-28 | 对应分支：feat/m2-gerrit-cgit-harbor（M3.0 增补自动化备份/恢复章节见 §6）
>
> 注：§1–§5 是 M0 时期的手动备份口径（LDAP/CA 单卷）；M3.0 起有覆盖 9 个卷的自动化脚本，见 §6，二者并存，自动化优先。

M0 单机底座的有状态数据集中在三个 Docker 命名卷；配置与镜像来源是仓库文件 + 远程 registry。备份分两类：**数据卷**（必须备份）与**配置真源**（随 git 走，单独留档）。

## 1. 有状态数据清单

| 数据 | 载体 | 是否必须备份 | 说明 |
|---|---|---|---|
| LDAP 目录数据 | 卷 `orgflow-minimal_ldap_data` | 是 | 用户/部门/ACL，唯一不可重建的业务数据 |
| LDAP 配置 | 卷 `orgflow-minimal_ldap_config` | 是 | slapd 运行配置（含首次引导结果） |
| CA 数据 | 卷 `orgflow-minimal_ca-data` | 是 | 内部 CA 私钥 + 站点证书；丢失需重新签发并更新信任链 |
| 配置真源 | 仓库 `config/`、`services/*/compose.yml`、`.env` | 建议 | `.env` 含口令，留在受控位置，勿入 git |
| 镜像 | GHCR digest `@sha256` | 否 | 远程可重新拉取；本地自建产物可重建 |

> 卷名前缀 `${COMPOSE_PROJECT:-orgflow-minimal}` 由 `up.sh` 注入，默认值见 `config/defaults.env`。若改了 project 前缀，下面命令中的卷名同步替换。

## 2. ⚠ 禁止热备份运行中的 LDAP 数据目录

**不要对 running 的 LDAP 容器直接 `docker cp` / `tar` 数据目录，也不要在容器写入时对卷做文件级拷贝。** OpenLDAP（slapd）的 `mdb` 数据库在写入过程中拷贝可能得到不一致快照，恢复后目录损坏。

正确做法二选一：

1. **停机一致性备份**（推荐，短中断）：先停 ldap 容器，再备份卷，完成后重启。
2. **逻辑导出**（不停机，推荐日常）：用 `ldapsearch` 导出 LDIF，恢复时重新导入。LDIF 是逻辑一致快照，不受 mdb 写入影响。

## 3. 备份命令

### 3.1 LDAP（逻辑导出，无需停机）

```bash
# 依赖 ldapsearch（宿主已装或进容器执行）；密码取 .env 的 LDAP_ADMIN_PASSWORD
LDAP_PW="$(grep '^LDAP_ADMIN_PASSWORD=' .env | cut -d= -f2-)"
docker exec -e BIND_PW="$LDAP_PW" of-ldap sh -c \
  'ldapsearch -x -H ldap://127.0.0.1 -D "cn=admin,dc=orgflow,dc=local" -w "$BIND_PW" -b "dc=orgflow,dc=local" -LLL > /tmp/backup.ldif' \
  && docker cp of-ldap:/tmp/backup.ldif ./backup/ldap-$(date +%F).ldif
```

> `dc=orgflow,dc=local` 为示例基 DN，按 `.env` 的 `LDAP_BASE_DN` 实际值替换。

### 3.2 LDAP 数据卷（停机一致性备份）

```bash
docker stop of-ldap                       # 短中断，避开使用时段
tar -czf backup/ldap-data-$(date +%F).tar.gz \
  -C /var/lib/docker/volumes/orgflow-minimal_ldap_data/_data .
tar -czf backup/ldap-config-$(date +%F).tar.gz \
  -C /var/lib/docker/volumes/orgflow-minimal_ldap_config/_data .
docker start of-ldap
```

### 3.3 CA 数据卷（可热备，CA 签发不频繁）

```bash
tar -czf backup/ca-data-$(date +%F).tar.gz \
  -C /var/lib/docker/volumes/orgflow-minimal_ca-data/_data .
```

### 3.4 配置真源

```bash
tar -czf backup/config-$(date +%F).tar.gz \
  config services .env Makefile up.sh scripts CHANGELOG.md
```

## 4. 恢复步骤

### 4.1 从 LDIF 恢复 LDAP（逻辑导入）

```bash
# 先确保 ldap 容器 healthy 且目录为空或已清空目标子树
docker cp ./backup/ldap-2026-11-24.ldif of-ldap:/tmp/restore.ldif
LDAP_PW="$(grep '^LDAP_ADMIN_PASSWORD=' .env | cut -d= -f2-)"
docker exec -e BIND_PW="$LDAP_PW" of-ldap sh -c \
  'ldapadd -x -H ldap://127.0.0.1 -D "cn=admin,dc=orgflow,dc=local" -w "$BIND_PW" -f /tmp/restore.ldif'
```

### 4.2 从卷快照恢复（停机）

```bash
docker stop of-ldap
# 清空卷再解包（务必确认目标卷名，避免写错服务）
sudo rm -rf /var/lib/docker/volumes/orgflow-minimal_ldap_data/_data/*
sudo tar -xzf backup/ldap-data-2026-11-24.tar.gz \
  -C /var/lib/docker/volumes/orgflow-minimal_ldap_data/_data
docker start of-ldap
# 健康确认
bash status.sh | grep ldap
```

### 4.3 恢复 CA

```bash
docker stop of-caddy of-router
sudo rm -rf /var/lib/docker/volumes/orgflow-minimal_ca-data/_data/*
sudo tar -xzf backup/ca-data-2026-11-24.tar.gz \
  -C /var/lib/docker/volumes/orgflow-minimal_ca-data/_data
docker start of-caddy of-router
```

> CA 恢复后若站点证书与当前 `DOMAIN` 不匹配，按 [证书与CA](证书与CA.md) 重新签发；不要复用过期证书硬起。

## 5. 备份有效性校验

- 每次备份后记录命令、退出码、产物大小到 `docs/records/执行日志/<日期>.md`。
- 每季度做一次**恢复演练**：在隔离环境用备份起一套，跑 `bash scripts/verify.sh` 的 LDAP/DNS 项确认数据完整。
- 备份产物存放位置须与本机磁盘故障域分离（异地/对象存储），否则卷与备份一起丢失。

## 6. M3.0 自动化备份与恢复（2026-11-28 新增）

### 6.1 口径

| 项 | 值 |
|---|---|
| RPO | 备份执行时刻（手动 `make backup` 触发）；RTO：隔离恢复 ≤5 min、全量重建 ≤60 min |
| 落点 | `/data/backups/<UTC>/`（本机第二路径；`BACKUP_ROOT` 可覆盖） |
| 备份卷（9 个） | `jenkins_home`、`registry_data`、`gerrit_git`、`gerrit_etc`、`ldap_data`、`ldap_config`、`selfcheck_reports`、`ca-data`、`registry_auth` |
| 不备份 | `builder_cache`（可再生）、Gerrit `index/db/cache`（index 可再生，db/cache 为运行时缓存） |
| Gerrit index（M3.0.1 T6） | `orgflow-minimal_gerrit_index`（named volume，index 可再生故不备份）；`down+up` 不再换空卷、无需手工 `make gerrit-reindex`；迁移脚本 `scripts/gerrit-index-migrate.sh` |
| 方式 | `tar czf` + `sha256sum` + `manifest.json`（卷名/大小/条目数/时间/commit/镜像 tag 快照），不引入新组件 |

> **已知风险**：备份落本机第二路径，单盘故障会同时丢失生产卷与备份。外送（rsync/NAS/对象存储）留到 M3.1 之后按需加。

### 6.2 备份与校验

```bash
make backup                         # 产出 /data/backups/<UTC>/，更新 latest 指针
make backup-verify                  # 校验最新：sha256 + 逐卷解包 + 条目数一致
make backup-verify BACKUP=/data/backups/<UTC>   # 校验指定备份
```

产物：`<vol>.tar.gz` × 9、`sha256sum.txt`、`manifest.json`。验收要求连续两次 `make backup` 成功、两次 `backup-verify` 全通过。

> **M3.0.4 备份单一入口、状态同源（F1/F2/F4）**：`scripts/backup-run.sh` 是**唯一备份入口**——`make backup` 与 `up.sh` 启动补跑都调它。每次备份都伴随一次校验与一次原子状态写入：`backup-run.sh` 记录 start/commit → 调 `backup.sh` 生成备份 → 调 `backup-verify.sh` 校验 → 一次性原子写 `/data/backups/status.json`（`backup` 绝对路径 / `backup_ts` / `exit_code` / `verify` / `bytes` / `volumes` / `commit` / `duration_sec` / `finished_at`），退出码即结果（0 成功 / 1 备份失败 / 7 校验失败）。`backup-verify.sh` 加 `BACKUP_VERIFY_NO_STATUS=1` 由单一入口调用时跳过自身 status 写入，避免双写竞争。`verify-backup` Job 增**断言 f**：`status.backup` 必须与 `/data/backups/latest` 内容完全一致，且 `status.finished_at` 与 latest 目录名时间差 ≤2h——防"旧状态套新备份"假绿。`up.sh` 补跑失败时状态已由 backup-run 写失败态，日志打印 `✗ [up] 启动补跑备份失败…selfcheck 将红`，但起栈仍 exit 0。`backup-daemon.sh` 的 `run` 常驻分支与全部固定时刻字样已删除，`deploy/systemd/orgflow-backup.{service,timer}` 残留已清理。

> **M3.0.3 备份去长定时（E2）**：M3.0.2 的 03:30 常驻守护（`backup-daemon.sh run` + watchdog + supervisor `orgflow-backup`）全部删除。备份改**手动** `make backup`（另有 `make backup-once`/`backup-status`/`backup-rotate`），`backup-daemon.sh` 只留 once/rotate/status/simulate（`run` 已在 M3.0.4 彻底移除）。`up.sh` 在全部服务 healthy 后同步检查 `/data/backups/latest` 年龄：>26h 或缺失就前台跑一次 backup-run.sh（日志 `[up] 启动补跑备份`）——这是一次性动作不是定时器，服务关停时不跑、重启后补上。`data-backup` 自检项保留（≤26h 仍判红，因服务活着时 up 已补跑、关停时自检也不会跑）。

> **M3.0.2 可信加固**：
> - **tar 重试归零**（D1）：`backup.sh` 每次 tar 尝试前显式 `rc=0`，两次都非 0 才失败；注入 `BACKUP_TAR_FAIL_ONCE=1` 可用于反证（第一次故意 rc=1、第二次 rc=0，整轮成功）。attempts 与两次退出码写入打包日志 `.tar-warnings.log`（保留供审计）。
> - **校验判红**（D2）：`backup-daemon.sh` 捕获 `backup-verify.sh` 返回码，非 0 时本轮 `exit_code=7`（专用码）+ `status.verify.ok=false`/`failures` 落盘，日志写 `verify failed` 并保留现场，不再打印"一轮备份完成"；`verify-backup` Job 增断言 e（`verify.ok=true` 且 `failures` 为空）。
> - **周备本地时区**（D3）：`weekly.flag` 按备份的**本地日期**（UTC 时间戳转 Asia/Shanghai 后取 `%u`）判定，不再用 UTC 星期（否则周日 03:30 备份在 UTC 仍是周六，周备 4 份策略成死代码）。marker 文件写 `local_date`/`weekday`/`backup_ts` 便于审计；`manifest.json` 增 `local_date`/`weekday` 字段。轮转遇到 `weekday` 非法（如 0）的 marker 跳过、不删、日志 `skip invalid marker`。
> - **changed_during_backup 阈值**：单卷 changed >20 记 WARN 写 status，>200 判本轮失败。

### 6.3 隔离恢复演练（只读生产，不启停容器）

```bash
make drill             # M3.0.3：前台手动跑隔离恢复真起栈（drill-up.sh）
                       # 输出 DRILL PASS/FAIL，退出码即结果；不注册任何调度。
# 结果：/data/drill/drill.result（字段化 JSON）+ /data/drill-logs/<ts>/drill-up.log
# M3.0.4：backup 字段绑定实际备份目录（失败也非字面 latest）；mode 恒 full（无 quick 空承诺）；
#         started_at/finished_at/duration_sec 为信息字段（Job 打印不判红）。
# 手动触发校验 Job（离线只读结果，无 cron）：
JENKINS_PASS='...' bash scripts/jenkins-trigger.sh verify-restore-drill
```

> **M3.0.3 演练改纯手动（E1）**：
> - **无定时、无守护**：M3.0.2 的 `drill-daemon.sh` + `drill-watchdog.sh` + supervisor `orgflow-drill` 全部删除；演练是**封版前的人工动作**，不是定时任务。服务随时可能被关停，任何依赖"昨夜已跑过"的设计都不可靠。
> - **数据来自备份**：`drill-up.sh` 从 `/data/backups/latest`（或指定备份）解包到 `/data/drill/orgflow-drill`，独立 project `orgflow-drill` + 独立网络起 gerrit/cgit/ldap 三容器，强制 healthy=3 + 四断言全过才输出 `DRILL PASS`。
> - **字段化结果**（E5）：`drill.result` 写 `result/ts/backup/log/healthy/repos/P_open/D_open/P_total/D_total/mode/backup_sha256/age_h`；`verify-restore-drill` Job 按字段断言（不 grep 中文文案），年龄 `age_h` **仅信息字段不判红**（缺结果或 FAIL 仍 FAILURE）。
> - **LDAP 口令闭环**（E4）：口令经 `docker exec -e` 注入，脚本/命令内无字面口令；容器内 `LDAP_ADMIN_PASSWORD` 与脚本读到的一致才通过；drill compose 删 `:-change-me` 兜底。
> - **changes 硬失败双指标**（E3）：SSH 私钥缺失/非 0/空/非数字直接 FAIL（注明 `ssh-key-missing`），`P_open==D_open` 且 `P_total==D_total`（total 用 `--format=JSON` 三状态查询），四数值写日志与结果。

> **发布检查表（人工把关，替代自检默认项）**：封版前须逐条确认并留痕：
> 1. `make backup` + `make backup-verify` 全通过（回滚点有效）；
> 2. `make drill` 输出 `DRILL PASS`（healthy=3 / repos=3 / P_open=D_open / P_total=D_total / backup_sha256 一致 / ldap rc=0），日志留档；
> 3. 手动触发 `verify-restore-drill` SUCCESS；
> 4. `make check`/`make test` 全绿；`selfcheck` 21 项全绿且报告无 data-drill 行；`JENKINS_PASS=... make verify-all` 手动巡检 21 项（排除 heavy）汇总无 FAIL；
> 5. 全仓库确认无 >5min 定时器与每日固定时刻守护。

### 6.4 生产全量重建（高风险，需停机窗口）

顺序不可颠倒，任一步失败即停并回滚：

1. **冻结**：`POST /job/verify-gerrit-review-flow/disable` 暂停 cron，公告冻结 gerrit-trigger 推送。
2. **备份校验**：`make backup && make backup-verify`。
3. **拆除保留卷**：`./down.sh`（默认保留卷；绝不 `--remove-volumes`）。
4. **从零拉起**：`./up.sh`。镜像须本地就绪：GHCR 主站不可达时用代理 `ghcr.nju.edu.cn` 拉取并 `docker tag` 成 compose 期望的 `ghcr.io/...` 名，再用 `./up.sh --no-pull`。
5. **Gerrit 索引（M3.0.1 T6 起无需手工重建）**：`index` 已改为 named volume `orgflow-minimal_gerrit_index`，`down+up` 保留同一卷、直接 healthy，不再需要 `make gerrit-reindex`。仅当 index 卷被误删/损坏时才手工重建（`make gerrit-reindex` 备用）。NoteDb 在 git 卷内（权威数据完整），index 可再生。
6. **恢复触发**：enable cron，跑一次端到端确认链路恢复。
7. **验收**：20 项自检 + 端到端 + 7 路径入口矩阵。

**回滚**：旧卷验收通过前不删除。任一步失败 → 停新栈 → 用旧卷重拉；卷数据损坏则从最近备份 `make restore` 恢复。

> **镜像 tag 漂移**：演练发现 compose/images.env 期望 `m2-gerrit:ctx-547cec6a8cd0`，线上长期运行 `m2-gerrit:3.9.0`（up 幂等未重建）。全量重建会切到 ctx tag（同为 Gerrit 3.9.0），须保证该镜像本地可用。
