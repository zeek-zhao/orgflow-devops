# AI 协作开发

> **读者**：用 AI 改这个仓库的人（当前就一位维护者），以及想知道「哪些结论能信」的评审者。
> **一页话**：AI 可以写代码、写文档、跑检查；**不能**做生产变更、不能合并、不能被当成验收人。
> 命令与硬约束在 [AGENTS.md](../AGENTS.md)，改代码的路径在 [工程开发说明](工程开发说明.md)。

---

## 1. 为什么单独写一份

这个仓库有全栈行为断言（数量以 `bats --count tests/bats/*.bats` 为准，不写死在这里）、
`make test` 的一串自检（清单在 `Makefile` 的 `test` 目标里）、3 个 CI 工作流。AI 参与之后，风险不再是
「写不出代码」，而是三件事：

| 风险 | 具体长什么样 | 代价 |
|---|---|---|
| **假绿** | 为了让它变绿，把断言改宽、加 `|| true`、跳过用例 | 门禁从此不可信，比没有门禁更糟 |
| **编判据** | 验收条件写成「确认功能正常」，或编一条不存在的命令 | 下次无法复现，等于没有验收 |
| **超范围** | 修一个 bug 顺手重构三个文件 | review 成本超过重写，且引进新问题 |

所以这份文档管的是**边界与责任**，不是提示词技巧。

## 2. 分工

| 活 | AI | 人 | 备注 |
|---|---|---|---|
| 读代码、定位、写实现 | ✅ | 复核 | AI 可以提方案，人可以否 |
| 写/改文档（含需求基线） | ✅ | 复核判据 | 判据必须能照抄执行 |
| 跑本地门禁（`make test` 等） | ✅ | 看结果 | 绿了不等于对，见 §4 |
| 写 bats / python 断言 | ✅ | 复核反证 | **必须附反证输出** |
| 改 CI 工作流 | ✅（PR 内） | 合并 | 改门禁属高风险改动，PR 正文要写清为什么 |
| 生产机操作（213 上 `make deploy`） | ⚠️ 可出命令 | **人来执行** | 见 §3 |
| 生成/轮换密钥 | ❌ | 人 | AI 不接触真值 |
| 合并 PR、关 issue | ❌ | 人 | 责任主体必须是人 |
| 重写 git 历史 | ❌ | 人（一次性决策） | 不可逆 |
| 判定「是否合规/可公开」 | ❌ | 人 | AI 可以列事实，不能下结论 |

## 3. 不能派给 AI 的活（清单，不解释）

- **生产变更**：在 213/214 上执行 `deploy / restore / down -v / rm` 这类动作。AI 可以给出**确切的命令与预期输出**，
  执行由人做。理由：这些动作没有回滚按钮，且失败信息往往延迟出现。
- **密钥与口令的真值**：不读 `.env`、不打印、不写进任何文件。仓库里只允许占位符与 `{SSHA}` 哈希。
- **删除数据**：卷、备份、分支、issue 历史。
- **合并与发布**：`main` 的合并、tag、GitHub Release。
- **合规判定**：「这份代码能不能公开」由人承担，AI 只提供可核实的证据清单。

## 4. AI 产出的验收：责任在人，证据在命令

一条改动「做完了」的判据不是「AI 说做完了」，而是三样东西同时成立：

1. **一条能照抄的命令**（不是描述），以及它的期望输出；
2. **一条反证**：故意改坏一处，命令必须变红（证明断言真的在跑）；
3. **适用边界**：这条命令在什么环境下不成立（例如需要 docker、需要真机、Windows 上会假红）。

只有第 1 条时，最常见的事故是「断言写错了方向，永远绿」。第 2 条正是为它准备的。

写进需求基线时同一条规则：判据挖不到就写「**判据缺失**」，不要编一条看起来合理的。

## 5. 派单怎么给（模板）

```
需求：REQ-M0-A4（docs/requirements/M0-A-身份与权限.md）
目标：<终态，不写实现步骤>
禁止：不得改 tests/images.lock / 不得放宽 16_jenkins.bats 的断言 / 不得动 config/routes.yaml
验收：<命令 + 期望输出>；反证：<改坏 X 必须红>
先只做取证，把发现列出来等我确认再改。
```

三个要点：

- **给需求号**，不给编号的活会变成「顺手重构」。
- **一次一件**。多件事混在一个分支里，红的时候分不清是谁的锅。
- **先取证后动手**。AI 最常见的浪费是「猜一个原因然后改三处」，取证能把三处减到一处。

## 6. 已知的失败模式（观察到过，别再犯）

| 失败模式 | 表现 | 正确做法 |
|---|---|---|
| 猜根因 | 看到 401 就改鉴权配置 | 先看日志/接口原文：401 可能只是口令不对 |
| 逐个打补丁 | 3 个用例红就改 3 处断言 | 同源失败先归因，一处改完三个都绿 |
| 降低标准 | 断言太严 → 放宽断言 | 先问「是判据错了还是实现错了」，判据错才改判据并在 PR 里说明 |
| 静默跳过 | 环境缺依赖就 `|| true` | 显式 skip 并打印「CI 会跑」，让人能看见 |
| 过长输出 | 贴 500 行日志当证据 | 贴能支撑结论的那几行 + 完整日志作为 artifact |
| 越界修改 | 修 bug 顺手重排文件 | 一个 PR 一件事，重构单独开 |

## 7. 与本仓门禁的关系

`AGENTS.md` 的硬约束全部有机械检查兜底，不靠自觉：

| 约束 | 机械检查 |
|---|---|
| 提交身份 / 无 AI 尾注 | `.githooks/commit-msg`、`make identity-check`、`Identity` 工作流 |
| 不直接推 main | `.githooks/pre-push`、ruleset |
| 文档登记完整 | `make docs-check` |
| 无内网标识 / 无凭据形态 | `make redaction` |
| 无死链 | `make links` |
| 全历史无密钥 | `Compliance` / `Secret Scan` 的 gitleaks |
| 行为没退化 | `make test-bats`（用例数见 `bats --count`） |

AI 产出的东西过不了这些检查，就不该进 `main` —— 这条没有例外，也没有「就这一次」。
