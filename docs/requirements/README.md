## 1. 这份文档与 GitHub Issue 的分工

**需求分两层，各管一件事，不许互相替代。**

| 层 | 在哪 | 回答什么 | 谁改 | 改的代价 |
|---|---|---|---|---|
| **需求基线**（本文与四个域文件） | 仓库 | 要求什么、怎么算做到 | 人，走 PR | 高：要求与判据冻结，改动即需求变更 |
| **执行状态** | GitHub Issue | 谁在做、卡在哪、什么时候关 | 任何人 | 低：随时改、随时关 |

为什么要拆：

- Issue 关掉之后，正文虽然还在，但**没人会去 diff 它**。「当时到底要求了什么」必须在仓库里有一份冻结的东西，否则半年后只能靠翻 issue 评论猜。
- 反过来，让仓库文档承担进度也不行：那样每推进一格就要改一次 md，最后必然变成「文档写着做完、实际没做」的假绿。

**双向指针是硬要求**：

- 基线每条需求有「证据」列，指向 Issue 号与 PR 号；
- 每个 Issue 头部写 `需求：REQ-M0-xx`（模板见 `.github/ISSUE_TEMPLATE/task.yml`）。

任一侧缺失，追溯链就断在那一格 —— 这正是 `deploy.sh` 把 `jenkins / 302` 写死、而 `#86` 之后实际变成 403 却没人发现的原因：**期望值和它对应的架构变更之间，没有指针**。

## 2. 编号规则

```
REQ-<里程碑>-<域><序号>       例：REQ-M0-A4
域：A 身份与权限 / B 流水线与交付 / C 呈现与文档 / D 底座与运维
```

- 编号**一经分配永不复用**。需求作废时保留行，`现状` 写 `已废弃`，并注明被谁取代。
- 编号与文件名解耦：域文件可以拆合，编号不变。
- 沿用 M0 已有编号（`A1–A6`、`B1–B5`、`C1–C2`）：代码与手册里已有 8 处正文引用，改编号等于制造 8 处死引用。
- 无编号的历史条目按域顺序补号（`A0`、`B0`、`B6–B9`、`D1–D7`），补号时在「证据」列写清它来自哪个 Issue，避免看起来像新需求。

## 3. 四列的语义（重要）

| 列 | 是否冻结 | 含义 |
|---|---|---|
| **要求** | 🔒 冻结 | 终态描述，不写实现步骤。改它 = 需求变更 |
| **验收判据** | 🔒 冻结 | 必须能照抄执行，且**至少有一条反证**。改它 = 降低或提高了验收门槛，同样是需求变更 |
| **现状** | 可变 | 见下表四个取值 |
| **证据** | 可变 | Issue / PR / 配置文件路径。**不抄长证据**——抄进来就会过期 |

`现状` 的取值只有四个，禁止自由发挥：

| 取值 | 判定依据 |
|---|---|
| `已实现` | Issue 已关闭，且有对应 PR 或仓内可机械验证的断言 |
| `部分` | 主能力已实现，但判据里明确列出的条目未全满足（**必须在要点里写清缺哪条**） |
| `未实现 · 转入 <里程碑>` | Issue 仍 open，能力缺口真实存在 |
| `已降级` | 曾计划做，明确决定不做，并写清理由 |

## 4. 判据的可复现性标记

判据前带 **⚠** 的，表示**在干净 clone 上跑不出来**，有三种原因：

| 标记 | 原因 | 处理 |
|---|---|---|
| ⚠ 需真机 | 依赖部署机运行态或浏览器人工操作 | 判据保留原样，另注「需真机」，不得写成「已验证」 |
| ⚠ 依赖已归档文档 | 判据原文引用了不随仓库分发的文档（按最小披露剔除） | 补一条可在仓内复现的替代判据 |
| ⚠ 判据缺失 | 当时没写判据，现在也补不出来 | 明确标「判据缺失」，**不许编一条看起来合理的** |

## 5. 变更控制

1. 改 `要求` 或 `验收判据`：同 PR 内加一行 `CHANGE-YYYY-MM-DD`，写清「谁要求、为什么改、旧值是什么」。
2. 只改 `现状` / `证据`：不需要 CHANGE 行，但必须在 PR 描述里写依据（Issue 关闭链接或命令输出）。
3. 需求作废：不删行，`现状` 改 `已废弃`，`要求` 列保留原文并追加 `→ 由 REQ-M0-xx 取代`。
4. 新增需求：先在本文件 §6 的索引表登记，再写进域文件，最后开 Issue。顺序反了就会出现「Issue 比基线多」。

## 8. 现状列的诚实声明

**`现状 = 已实现` 的判定依据是「Issue 已关闭 + 有 PR」，不是本轮逐条重跑验收。**

本轮（2026-11-11）实际复核过的只有两类：

- 仓内可机械验证的部分（`grep` 计数、bats 文件存在与否与用例数）——这部分写进判据列，可随时重跑；
- 与 CI 状态相关的事实（见 [问题索引](../project/问题索引.md)）。

**没有复核过**：需要在部署机上跑起来的运行时行为、需要浏览器的登录链路。这些条目一律标 `⚠ 需真机` 或依赖 Issue 关闭这一事实，不额外宣称。

这一条写在这里，是因为本仓库已经吃过一次「CI 全绿 + 文档写已完成 + 真机 `make deploy` 直接失败」三者同时成立的教训。
