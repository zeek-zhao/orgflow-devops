## 1. 分解口径

WBS 只到「可交付物」这一层，不再往下拆到人天：

```
需求域（REQ-M0-A/B/C/D）→ 工作包（一组同源改动）→ 交付物（PR / 配置项 / 文档）
```

「同源改动」的判据是**改一处要动哪几个文件**，见 [工程开发说明](../工程开发说明.md)。
工作包不是排期单位，是**影响分析单位**：变更控制时用它判断波及范围。

## 3. 里程碑准入 / 准出

里程碑是**范围容器**，不是时间盒；tag 是发布点，两者刻意分开（[项目管理](../项目管理.md) §5）。

| 阶段 | 准入 | 准出（全部满足才可关） |
|---|---|---|
| 开启 | 有一组编号完成的 REQ 与对应 Issue | — |
| 实施中 | 每条 open issue 能指出改哪份文档、哪段代码 | — |
| 关闭 | 该批每条需求都有「现状」与证据指针 | `gh issue list --milestone M0 --state open` 为空 |
| 关闭 | 未完成项已先转入下一批需求文档 | 下一批基线中能查到转入行 |
| 关闭 | 三层验证与公开面门禁通过 | `make check-all`、`make redaction`、`make links` 绿 |
| 关闭 | 交付物与登记册一致 | `make docs-check` 绿 |

「关了但没做完」是禁止状态：要么写清还剩什么再关，要么留在 open 并标 `state/blocked`
说明卡在谁身上（[项目管理](../项目管理.md) §3）。

## 5. 进度复核（三条命令，不建表）

```bash
gh issue list --state open
grep -c 已实现 docs/requirements/M0-*.md
git log --oneline -10
```

每周核对三件事：open issue 里有没有「其实已经做完但没关」的；
需求行「现状」与 issue 状态是否一致（不一致以判据为准）；
`state/blocked` 有没有超过两周没人动的（解卡或转 icebox 并写复活条件）。
原口径见 [项目管理](../项目管理.md) §7，本文不另立一套。

## 6. 变更与追溯

工作包范围变化走 [项目管理](../项目管理.md) §9 的统一变更控制：
先写影响分析（波及哪些工作包、哪些配置项、哪些门禁期望值），再写 CHANGE 行，
最后同步 Issue 与 PR。**只有实现变了而范围没变**，不算里程碑变更，按缺陷处理见 [问题索引](../问题索引.md) §6。
