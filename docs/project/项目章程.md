## 1. 立项依据

一套单机自托管的 DevOps 平台：Caddy + oauth2-proxy + Dex + OpenLDAP + Jenkins + Nexus +
dnsmasq，用 `docker compose` 编排，镜像由 GitHub Actions 构建后推到 GHCR、部署机只拉不构建。
目标是让「身份、路由、流水线、制品仓库、备份」在同一台机器上可复现地自举，
并且**每个结论都能被一条命令复现**（见 [AGENTS.md](../../AGENTS.md)）。

立项要解决的不是「装一套工具」，而是三件已经发生的事：CI 全绿但真机部署失败、
验收脚本的期望值随架构变更静默过期、文档与过程记录混在一起导致接手人分不清哪个能信。
这三件事分别在 [M0 测试体系](../engineering/M0-测试体系.md)、[文档规范](../engineering/文档规范.md) §7.1、
[文档规范](../engineering/文档规范.md) §1 里留有成因记录。

## 3. 范围边界

| 在范围内 | 不在范围内 |
|---|---|
| 单机 10 个 compose 服务 + 由 job 拉起的制品仓库 | 多机集群、高可用、跨地域容灾 |
| 域名路由 + 内部 CA 的网关模型 | 公网可信证书、公共 DNS 解析 |
| GHCR 镜像分发与 `@sha256:` 锁定 | 本地构建并推送镜像、私有 Registry 运维 |
| 参数化 Job 与 `make` 两套操作入口 | 自研 UI、看板、工单系统 |
| 仓库内 `docs/` 的规程与参考文档 | 会话交接、待办、验收过程记录（按最小披露移出） |
| 单一维护者的提交身份与审计链 | 多人协作审批流、外部贡献者 DCO |

「不在范围内」不是「永远不做」，是**本批次不承诺**。复活条件写在对应 Issue；
里程碑口径见 [项目管理](项目管理.md) §5。

## 4. 假设与约束

| 类别 | 内容 | 违反时的表现 |
|---|---|---|
| 运行环境 | 部署机有 Docker 与内网 DNS，网关域名解析到本机 | 站点 308 跳转或域名不通 |
| 构建 | 镜像在 CI 构建，部署机不本地构建 | `make images-guard` 报「已提交未构建」 |
| 身份 | author 与 committer 唯一，合并用 Rebase | `make identity-check` 红、Identity 工作流红 |
| 凭据 | 真实口令只在部署机 `.env`，仓库只存占位符与哈希 | `make redaction` 红 |
| 公开面 | 记录层 0 篇，过程取证不随仓库分发 | 内部流程文档回流判红 |
| 网络 | 跨机访问只经网关端口，不假设管理端口可达 | 直连验收必须用网关端口做兜底 |

## 5. 干系人与职责（RACI）

| 角色 | 谁 | 负责 R | 批准 A | 咨询 C | 知会 I |
|---|---|---|---|---|---|
| 维护者 | 仓库所有者 | 需求、实现、发版、关单 | 全部合并与发布 | — | — |
| 外部只读者 | 公开仓访问者 | — | — | 通过 Issue 报告缺陷 | 发布说明 |
| 安全报告者 | 通过私密通道提交者 | — | — | — | 处理进展见 [SECURITY.md](../../SECURITY.md) |
| AI 助手 | 协作工具 | 实现、文档、断言、跑门禁 | — | — | 产出须附命令与反证 |

AI 不可做的六类事（生产变更、密钥真值、删数据、合并发布、合规判定、重写历史）
见 [AI 协作开发](../engineering/AI-协作开发.md)。**合规判定由人做**，AI 只提供可复现的取证。

## 6. 沟通与决策

| 事项 | 载体 | 频率 / 触发 |
|---|---|---|
| 要求与判据 | [需求基线](../requirements/README.md) | 冻结，改即变更 |
| 状态与卡点 | GitHub Issue | 随时 |
| 交付与证据 | Pull Request | 每次合并 |
| 架构决策 | ADR（见 [ADR-13](../records/ADR-13-域名路由.md)） | 架构性变更时 |
| 变更裁决 | [项目管理](项目管理.md) §9 统一变更控制 | 每次需求、配置、文档变更 |
| 每周自检 | `gh issue list --state open` 等三条命令 | 每周 |
| 漏洞报告 | [SECURITY.md](../../SECURITY.md) | 随时 |

决策原则：**单一维护者裁决，但裁决必须留下可 diff 的痕迹**。Issue 能改但没有 diff，
所以「当时要求了什么」留在需求基线，「谁裁决的」留在 PR 与 CHANGE 行。
