# 质量管理计划

> 规程性质：怎么定义「合格」、用什么机制守住合格。状态与复审节奏见[文档登记册](../文档登记册.md)。

## 1. 质量目标

- 每个结论都能被一条命令复现（本仓库的元约束，见 [AGENTS.md](../../AGENTS.md)）；
- 需求判据红绿边界清晰：每条 REQ 有验收判据与反证（[requirements/](../requirements/README.md)）；
- 门禁红必须归因修复，**不得为了让检查变绿而放宽断言或删用例**——假绿比红更贵。

## 2. 质量控制机制（谁在守）

| 层 | 机制 | 内容 |
|---|---|---|
| 提交前 | `make check` | 文档配置/死链/脱敏/标签清单（秒级） |
| 推送前 | `make check-all` | 快检查 + 单测 + lint + DinD 全栈（`SKIP_BATS=1` 可跳 bats） |
| CI | Test / Compliance / Identity | DinD 70 用例、SBOM/密扫、提交身份审计 |

分层细节与红项归因方法见[CI 门禁分层](../engineering/CI门禁分层.md)。

## 3. 红项处理（反证硬要求）

1. 先取证再改：红分**真缺陷 / 判据假红 / 环境差异**，三类改法完全不同；
2. 假红必须修门禁本身，不是加 `|| true`；
3. 修完贴反证：**改坏一处 → 红；恢复 → 绿**，只贴绿的那半不算验证；
4. 三条以上同源失败，先停写根因，不逐个打补丁。
   历史案例（CodeQL 数据流告警、DinD 卷泄漏等）收在[经验教训](../engineering/经验教训.md)。

## 4. 质量记录

- 验收证据：PR 的 CI run、真机验收报告（如《全新部署验收报告-2026-11-15》）；
- 服务级验证对应关系：[服务×需求×测试矩阵](../engineering/服务×需求×测试矩阵.md)；
- 测试体系与准出判据：[M0-测试体系](../engineering/M0-测试体系.md)。
