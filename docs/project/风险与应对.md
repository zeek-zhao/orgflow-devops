# 风险与应对

> 状态：review ｜ 负责人：zeek.zhao ｜ 层级：规程（DOC-P-012）
> 登记与状态见 [文档登记册](../文档登记册.md)，立项边界见 [项目章程](项目章程.md)。
>
> **本文是规程，不是记录层台账**。仓库的 [记录层 0 篇](../文档登记册.md) 是有意决策，
> 且 `scripts/gen_docs_site.py` 会把 `docs/**/*.md` 全量编入公开站点；
> 风险条目因此不写成「某天的状态快照」，而写成**可复现的查询命令 + 指向 Issue**。

## 1. 识别与分级

| 等级 | 判定（概率 × 影响） | 处置时限 | 谁裁决 |
|---|---|---|---|
| 高 | 已在门禁中判红，或会让公开面出现凭据/内网标识 | 本轮内 | 维护者 |
| 中 | 判据没跟上架构变化、依赖上游未修复、需人工确认 | 下次发版前 | 维护者 |
| 低 | 有明确缓解且不影响交付 | 月度复核 | 维护者 |

分级看**能不能被一条命令复现**，不看主观严重度。写不出复现命令的先归为「待取证」，
不要凭印象升级或降级。

## 2. 四种应对

| 策略 | 适用 | 落地形态 |
|---|---|---|
| 规避 | 义务不该由本仓承担 | 范围边界写进 [项目章程](项目章程.md) §3，例如不宣称符合 CRA |
| 缓解 | 不能消除但能压住 | 门禁脚本 + 反证，例如 `scripts/check-actions-pinned.py` |
| 转移 | 需上游或平台侧修复 | 开 Issue 并写清「以谁的名义对第三方发言」由人决定 |
| 接受 | 有证据、暂不处理 | 写进 [开源合规](../records/开源合规.md) §5 已知不一致，并给出复核命令 |

**接受不等于忽略**：每条被接受的风险必须带一条能查它是否还成立的 grep / API 调用。

## 3. 复核节奏

| 频率 | 动作 | 命令 |
|---|---|---|
| 每次 PR | 门禁红项按三类归因 | `make check`、`make check-all` |
| 每次发版 | 公开面与供应链 | `make redaction`、`make sbom`、`make cve` |
| 每月 | 登记册 WARN 与风险条目复核 | `make docs-check`、`gh issue list --label state/blocked` |
| 每季度 | 规程本身是否过期 | `make docs-check` + 人工过一遍本文 §4 |

## 4. 当前风险条目（用命令查，不抄快照）

| 风险 | 等级 | 复现命令 / 出处 | 应对 |
|---|---|---|---|
| 分发镜像已知漏洞 | 高 | `make cve`，报告在 `out/cve/` | 接受并出账，阈值待基线建立；见 [开源合规](../records/开源合规.md) §10 |
| 镜像 digest 落后源码 | 高 | `make images-guard` | 缓解：先合并、等 Images 工作流、`make images-pin` |
| 门禁判据没跟上路由变化 | 中 | `make test-bats`，看 `tests/bats/14_caddy.bats` | 按 [问题索引](问题索引.md) §6 归类为「判据没跟上变化」，修门禁并贴反证 |
| 期望值随架构变更静默过期 | 中 | `make docs-check` 的 WARN 列表 | 缓解：见 [文档规范](../engineering/文档规范.md) §7.1 |
| 弱口令哈希可离线爆破 | 中 | `scripts/test_ldif_passwords.py` | 缓解：随机口令 + 独立 salt + 弱口令断言；见 [开源合规](../records/开源合规.md) §7 |
| 上游组件许可证标注不一致 | 中 | 见 [开源合规](../records/开源合规.md) §5 | 接受并记录，是否向上游反馈由人裁决 |
| 备份包归档口径变更 | 低 | 见 [备份与恢复](../engineering/备份与恢复.md) | 已隔离旧包，复核时确认新包口径 |
| 平台侧安全开关 PATCH 返回 200 但不生效 | 低 | 见 [开源合规](../records/开源合规.md) §11 | 接受，改设置后必须再 GET 比对 |
