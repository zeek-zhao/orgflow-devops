# 项目管理

> **读者**：维护者自己，以及要看懂「这个仓库怎么组织工作」的评审者。
> **一页话**：要求写在 `docs/requirements/`（冻结、可 diff），执行状态写在 Issue（活、有时间线），
> 交付写在 PR。三者用需求号串联，**不用看板**，靠三条命令自检。

---

## 1. 三层对象，各管一件事

| 层 | 落在哪 | 回答什么 | 能不能改 |
|---|---|---|---|
| **要求** | `docs/requirements/M0-*.md` | 要求什么、怎么算做到 | 「要求」与「验收判据」列**冻结**，改即变更 |
| **状态** | GitHub Issue | 谁在做、卡在哪、什么时候关的 | 随时改，这就是它的用途 |
| **交付** | Pull Request | 具体怎么改的、证据在哪 | 合并后只读 |

为什么不让 Issue 当唯一真本：Issue 正文能改但没有 diff，半年后没人知道「当时到底要求了什么」。
为什么不让仓库文档管进度：那会变成每天改 md，且和 Issue 双头维护。

**双向指针**：需求行里写 Issue 号；Issue 用模板的「需求号」字段写 `REQ-M0-xx`。
`docs/问题索引.md` 是这张映射的汇总视图。

## 2. 编号

```
REQ-<批次>-<域><序号>      例：REQ-M0-A4（M0 批次，A 域，第 4 条）
域：A 身份与权限 / B 流水线与交付 / C 呈现与文档 / D 底座与运维
```

- 编号**一经分配永不复用**。删掉的条目保留一行并标 `archived`。
- 派生编号：`BUG-<Issue号>`（实现错，需求没错）、`DOC-*`（文档，见 [文档规范](文档规范.md)）。
- 编号与文件名解耦：文件名可以改，编号不变 —— 这是引用能活过重构的原因。

## 3. 状态机

需求行的「现状」只有四个取值，**没有第五个**：

| 现状 | 含义 | 谁负责推进 |
|---|---|---|
| `已实现` | 判据全部通过，且证据指针可在 5 分钟内复核 | — |
| `部分` | 主要能力在，但有判据不成立（行内必须写明缺哪条） | 对应 Issue |
| `未做` | 没开工 | 对应 Issue / 里程碑 |
| `转入 M1` | 明确不在本批范围 | M1 的需求文档 |

Issue 侧只有 `open` / `closed`。**「关了但没做完」是不允许的状态** —— 要么写清还剩什么再关，
要么留在 open 并标 `state/blocked` 说明卡在谁身上。

## 4. 标签（四类，固定集合）

| 前缀 | 回答 | 取值 |
|---|---|---|
| `type/` | 做什么 | feat·fix·docs·ci·refactor·test·chore·decision·manual |
| `prio/` | 多急 | P0（main 红 / 口径错）·P1（本轮必备）·P2（可延后） |
| `area/` | 哪一块 | identity·pipeline·presentation·ops·compliance |
| `state/` | 卡在哪 | blocked（写清卡点）·icebox（冻结 + 复活条件） |

真本是 [`.github/labels.json`](../.github/labels.json)，改标签必须走 `make labels-sync`；
`make test` 里的 `scripts/test_labels.py` 校验清单自洽、模板引用已声明。

不使用无前缀标签。历史遗留的 `bug` / `ci` / `documentation` / `task` 保留在原 Issue 上作为记录，
但不再新增。

## 5. 里程碑

一个里程碑 = **一批需求 + 一组验收**，不是时间盒。

| 里程碑 | 范围 | 状态 |
|---|---|---|
| M0 | 10 个服务起得来、能登录、能部署/备份/恢复、可公开 | **closed**（2026-11-11，36 完成 / 0 转入 M1；2026-11-12 裁决将原转 M1 的 B9/D7 收回 M0 实现，见 PR #138 与 #141） |
| M1 | 只读根、便携化（视图分类 / 双节点 / Nexus docker·pypi 已随 PR #138 回 M0 实现） | open |

规则：

- 里程碑关闭前，`docs/requirements/` 里该批每条需求必须有现状与证据指针。
- 未完成项**先转入下一批的需求文档**，再关里程碑 —— 不能只改里程碑了事。
- tag 与里程碑不是 1:1：里程碑是「范围容器」，tag 是「发布点」。两者刻意分开。

## 6. 需求变更

改一条已冻结的需求，要走同一套流程：

1. 在条目下加一行 `CHANGE 2026-11-11：<改了什么> —— <为什么>`，保留原文（不要就地覆盖）。
2. 同步 Issue（改标题/正文或新开一条）。
3. PR 里说明这是**需求变更**而不是实现变更。

反过来，实现与判据不一致时必须分类：**判据错**（改判据，写 CHANGE）还是**实现错**（改代码，开 BUG）。
判不出来就停下来写成 issue，别猜。

## 7. 没有看板，怎么知道进度

看板的价值是「一眼看全」，代价是每次状态变更要拖一次、且与需求文档双头维护。
单人维护下用三条命令代替：

```bash
gh issue list --state open                       # 还开着什么
grep -c '| `已实现` |' docs/requirements/M0-*.md  # 需求层面做完了多少
git log --oneline -10                            # 最近实际在改什么
```

每周核对一次三件事：

- [ ] open issue 里有没有「其实已经做完但没关」的（多半是忘了回写结论）
- [ ] 需求行的「现状」与 issue 状态是否一致（不一致以判据为准，改现状并写原因）
- [ ] 有没有 `state/blocked` 超过两周没人动的（要么解卡，要么转 icebox 并写复活条件）

## 8. 与其它文档的边界

| 想知道 | 去哪 |
|---|---|
| 这条需求要求什么、怎么算做到 | [requirements/](requirements/README.md) |
| 某个 Issue 该改哪份文档、哪个文件 | [问题索引](问题索引.md) |
| 文档怎么编号、怎么退役 | [文档规范](文档规范.md) |
| 代码怎么改、改完跑什么 | [工程开发说明](工程开发说明.md) |
| AI 能做什么、不能做什么 | [AI-协作开发](AI-协作开发.md) |
