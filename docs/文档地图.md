## 哪些内容不在这个仓库里

原先有一批内部记录文档（会话交接、待办、验收记录、增量需求总表、派单流程、
任务卡、账号与登录、身份命名规范、提交规范）：它们记的是「某天的状态」与
「内部怎么派工」，既会过期，也不适合跟着代码一起对外。

现在它们不随仓库分发。判断一条信息该去哪：

| 信息性质 | 去处 |
|---|---|
| 系统**应该**怎么设计、怎么运行 | 本仓库（ADR / 服务手册 / 设计说明） |
| **要求过什么、怎么算做到** | [需求基线](requirements/README.md)（只写要求与判据，不含内网取证与派工细节） |
| 某次**验证**的过程与取证 | 不外发；结论写进对应的设计文档或 Issue |
| 谁在什么时候做什么 | Issue / PR，不再另建文档 |
| 一次性的一次性状态快照 | 不留存 —— 需要时看 `git log` 与 Issue 时间线 |
| 风险台账的每日状态 | 不外发；规程里只留复现命令，见 [风险与应对](project/风险与应对.md) |

> 需求基线不是当年那份「增量需求总表」的原样回流。旧表含内网实测取证、决策过程与派工细节，
> 按最小披露不分发；现在的基线只保留**要求、验收判据、现状、证据指针**四列。

## 四个常见误区

1. **拿「某次验证记录」当设计文档**：它记的是「那天验过什么」，不是「系统应该怎么设计」。
   设计意图在 [M0-最小核心](M0-最小核心.md) 与 [ADR-13](ADR-13-域名路由.md)。
2. **拿「状态快照」当权威**：快照会过期。冲突时以代码、`config/`、`docker-compose.yml` 为准。
3. **改了架构只改手册**：顺序必须是 ADR → 服务手册 → 入口索引。反过来就会出现
   「手册比 ADR 新」的矛盾态，下一个接手人只能猜哪个对。
4. **以为放进子目录就不用登记**：`docs/project/`、`docs/engineering/` 里的每篇都在
   [文档登记册](文档登记册.md) 里，路径按 `docs/xxx/yyy.md` 原样写。漏一行 `make docs-check` 就红，
   而且 `scripts/gen_docs_site.py` 会把 `docs/**/*.md` 全量编进对外站点 —— 子目录不是私有区。
