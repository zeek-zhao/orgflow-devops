## 1. 分发事实（义务的触发点）

合规义务只在「分发」发生时触发，所以先确认事实，而不是假设。

本项目把 13 个容器镜像推送到 GHCR（`ghcr.io/zeek-zhao/orgflow-devops/*`），
且这些包**匿名可拉取**（不带任何凭据即可换到 pull token）：

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  "https://ghcr.io/token?scope=repository:zeek-zhao/orgflow-devops/mirror-homepage:pull&service=ghcr.io"
# → 200
```

**结论：对公众的分发已经发生**，GPL-2.0 / GPL-3.0 / EPL-1.0 的义务此刻即生效，
不因为「仓库还是 private」而豁免。仓库可见性与镜像可见性是两件事——这一点最容易误判。

## 3. 维护规则（不遵守就会退回 D 级）

**新增或升级任何组件时，必须同步三处，缺一即视为声明不可信：**

1. `licenses/` —— 新增 copyleft 组件的许可证全文
2. `THIRD_PARTY_NOTICES.md` —— 组件、版本、上游地址、义务
3. `scripts/gen-sbom.py` 的 `DECLARED` 表 —— 机器可读的许可证声明

升级镜像时另有第四处：`tests/images.lock`（digest）与 `docker-compose.ghcr.yml`。

判定「新组件是不是 copyleft」不要看镜像 label：**实测 `sonatype/nexus3` 的 label 写
`Apache-2.0`，上游 `LICENSE.txt` 是 EPL-1.0**。要看上游仓库的 LICENSE 原文。

## 4. 验证命令（发布前四条，缺一不可）

```bash
bash scripts/check-public-redaction.sh .   # 公开面门禁：内网标识 / 凭据形态 / 内部文档
make links                                 # 仓内文档链接自洽（无 404）
make docs-check                            # 文档登记册：双向一致 / ID 唯一 / 状态有见证
make sbom                                  # 声明式 SBOM（12 个镜像）
make cve                                   # CVE 扫描（需 trivy；未装会明确失败，不假装干净）
```

`make cve` 在没装 trivy 时 **exit 3**，不是 exit 0 —— 「没扫」和「扫过且干净」必须能区分，
否则这套合规声明自己就不可信。

脱敏门禁的正反两面都有记录（2026-11-11）：

- 反面：`scripts/` 下任一文件写入真实内网网段 → rc=1；把 `docs/账号与登录.md` 加回来 → rc=1
- 正面：清空后 rc=0，且**不会**因为 `172.31.0.*`（compose 网段）或 `zeek.zhao`（公开身份）误报

## 4.1 门禁规则为什么这么定（废止了三条旧规则）

门禁最早是「双仓导出」时代的产物，规则按导出目录那套写的。单仓化之后公开面就是仓库本身，
沿用旧规则会**用错误的标准做正确的事**，所以重定了三条：

| 旧规则 | 现在 | 理由 |
|---|---|---|
| 拦 `172.31.0.*` | **移出** | 这是 compose 自己的容器网段，ADR-13 整篇在讲它。按旧规则执行等于改掉整套网络设计 |
| 拦 `zeek.zhao` | **移出** | 仓库公开后它就在每条提交的 author 里；文档里抹掉是自欺，还会和 `git log` 互相矛盾 |
| 拦「导出目录里的死链」 | 改成**仓内死链** | 没有导出环节了 |

保留并加强的：真实内网网段 `10.22.<x>.0/24`、内部主机名、内网组织域名、PAT/AWS key/私钥块、
口令明文，以及「内部流程文档不得存在」这一条独立判据 —— 最后一类可能整篇加回来却不含任何
敏感串，只靠模式匹配会漏。

## 4.2 密钥扫描的豁免口径（`.gitleaks.toml`）

`Compliance` 与 `Secret Scan` 两个工作流跑的是**全历史** gitleaks。历史里出现命中时，
只有两条路：改历史，或者说明白为什么这条不是凭据。当前选了后者，共 3 条，全部进
`.gitleaks.toml` 的 allowlist：

| 命中 | 是什么 | 为什么不是凭据 |
|---|---|---|
| `curl-auth-user` × 2 | `scripts/jenkins-cli.sh` 注释与 `docs/services/jenkins.md` 资料表里的 `curl ... --user USER:TOKEN` | Jenkins 官方文档的逐字示例，`USER:TOKEN` 是占位符；这两处的上下文恰恰在写「凭据不进 argv」 |
| `generic-api-key` × 1 | `.env.example` 旧版的 `OAUTH2_COOKIE_SECRET=0123456789abcdef0123456789abcdef` | 顺序十六进制占位串，从未用于任何环境；当前值已改为低熵 `change-me-...` |

豁免**按行内容**做（`regexTarget = "line"`），不豁免整个文件 —— 同一个文件以后出现别的
形状的密钥照样会被抓。签入任何一条豁免都必须附反证，本轮的三组对照（在 GitHub 全新克隆上跑）：

```bash
gitleaks git . --redact --log-opts=--all                        # rc=1，3 条  ← 复现 CI 的红
gitleaks git . --config .gitleaks.toml --redact --log-opts=--all # rc=0        ← 豁免生效
# 再往历史里塞一个假的 ghp_ 令牌 → rc=1，1 条                  ← 豁免没有把规则关掉
```

第 3 组是必须的：只证明「变绿」而不证明「仍能红」，等于把扫描器关掉却说是修好了。

## 7. 公开前必须同时成立的三件事（顺序不能换）

1. **历史重写**：真实内网网段、内部主机名、初始口令曾出现在 30 个历史提交里。
   清工作区 ≠ 清历史 —— 点「公开」那一刻历史永久可见，且无法撤回。
   所以用 `git filter-repo` 重写全部提交（删内部文档路径 + 替换敏感串），SHA 全变。
2. **内部流程文档剔除**：会话交接 / 待办 / 验收记录 / task-cards / 账号与登录 等含内网拓扑
   与验收取证过程，按最小披露不再随仓库分发。注意：**删文件不等于删历史**，
   必须和上一步一次做完，否则旧提交里仍然读得到。
3. **初始口令离开仓库**：`users.ldif` 原先存的是「10 个账号共用同一个六位弱口令」的哈希，
   而那个口令当时在部署机上真在用。现在仓库只存随机不可用口令的哈希，真值在 `.env`
   （`ORGFLOW_INITIAL_PASSWORD`），`make ldap-passwords` 负责让两者一致。

第 3 条同时翻转了一条测试的判据：`scripts/test_ldif_passwords.py` 原要求「哈希必须等于
某个特定口令」，那等于在**保护**一个弱口令；现在改成弱口令黑名单 + salt 互不相同。

## 8. 公开之后新增的义务（2026-11-11 起）

仓库从 private 转 public 之后，有三条义务是之前不存在的：

| 义务 | 为什么 | 现在怎么满足 |
|---|---|---|
| **服务端强制提交身份** | 本地钩子可被 `--no-verify` 绕过；公开仓才解锁 ruleset | 见 #129：ruleset 限制作者可合并、禁止直推 main |
| **漏洞报告有私密通道** | 公开之后安全问题的报告人会走 GitHub Security Advisory | [SECURITY](../SECURITY.md) 指向私密渠道；secret scanning 与 Dependabot alerts 已可开启 |
| **密钥扫描覆盖全历史** | 公开 = 历史永久可读，历史里的密钥等于现在泄漏 | `Compliance` 每次 push 跑 gitleaks 全历史，豁免口径见 §4.2 |

**不因为公开而改变的**：许可证与再分发义务在 private 时期就已存在（对外分发的触发点是「交付给他人」，
不是「公开仓库」）。公开只是让义务变得可被外部核对。

## 9. CRA（EU 2024/2847）映射：现在到哪一步

CRA 对「有数字元素的产品」要求漏洞处理流程、SBOM、协调披露与安全更新期。本仓当前状态：

| CRA 要求 | 现状 | 缺口 |
|---|---|---|
| 软件物料清单（SBOM） | `make sbom` 生成 SPDX 2.3（12 个镜像） | 只覆盖镜像，未含 Jenkins 插件与 python 依赖 |
| 漏洞处理流程 | CI 有 `make cve`（trivy），未装时 exit 3 | 没有「发现→评估→修复→披露」的时间线记录 |
| 协调漏洞披露 | `SECURITY.md` 给私密渠道 | 没有响应时限承诺（建议 90 天） |
| 安全更新分发 | 镜像由 CI 构建，tag 语义清晰 | 没有明确的支持期声明（M0 阶段可写「不承诺」） |
| 技术文档与合规声明 | 本文件 + `THIRD_PARTY_NOTICES.md` | 未出具正式符合性声明（非商业项目，暂不宣称符合） |

**口径**：M0 不宣称符合 CRA，只逐条列出差距。把「没做」写成「做了」是最贵的一类错误。

## 10. 供应链的三段缺口：SBOM → CVE → VEX

三段是链条，断在任何一段，前面都白做：

1. **SBOM**：能列出「这个镜像里有什么」。已有（声明式 SPDX，由 `scripts/gen-sbom.py` 生成）。
2. **CVE 关联**：能回答「我受影响吗」。**缺**。trivy 扫的是镜像，与 SBOM 里的组件没有建立映射，
   所以「某个 CVE 出现在 trivy 报告里」和「它在我的 SBOM 里对应哪个组件」无法自动对应。
3. **VEX**：能回答「受影响但我为什么不用修」。**缺**。没有 VEX 文档，意味着每个 CVE 都要人工判断，
   且判断结果不进仓库 —— 下一个人要重新判一遍。

已在 #133 立项，M0 不做。判断依据：这三段的价值随组件数量增长，而当前栈只有 12 个镜像 +
22 个 Jenkins 插件，人工可覆盖；先补齐「SBOM 条目 → 组件坐标」的映射，再谈 VEX。
