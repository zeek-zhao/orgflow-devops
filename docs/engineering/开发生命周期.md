## 1. 阶段门总表

| 阶段 | 准入 | 准出 | 一条复现命令 |
|---|---|---|---|
| 需求 | 有编号与冻结的要求/判据 | 每条有证据指针 | `grep -c 已实现 docs/requirements/M0-*.md` |
| 设计 | 架构性变更已写 ADR | ADR 头部有「因何而起」 | `make docs-check` |
| 实现 | 有对应 Issue 与分支 | 改动集中在工作包内 | `git status -s` |
| 验证 | 三层验证各有判据 | 门禁全绿 + 反证齐 | `make check-all` |
| 评审 | PR 描述写清「为什么」 | 身份合规、无 AI 尾注 | `make identity-check` |
| 合并 | 必需检查全绿 | Rebase 合入，不 Squash | `git log --oneline -10` |
| 发布 | 发布准入清单通过 | SBOM/CVE 出账、digest 回写 | `make images-guard` |
| 运维 | 备份与恢复演练通过 | 排查入口可达 | `make backup-verify` |

阶段不是瀑布：**允许小步循环，但每次合并必须走完验证到评审四道门**。
跳过门禁的代价写在 [CI 门禁分层](CI门禁分层.md) §1。

## 3. 提交消息

```
type(area): 一句话说清改了什么
```

`type` 取 `feat` `fix` `docs` `ci` `refactor` `test` `chore`；
`area` 取 `identity` `pipeline` `presentation` `ops` `compliance` `docs` `project`。
diff 已经说了「改了什么」，正文只说「为什么」与「怎么验证的」。

## 4. 不做的事（写下来是因为被问过很多次）

- 不在本地构建镜像（`make build-local` 只验证 Dockerfile，产物不推 GHCR）
- 不手工 `docker run` 起 ldap / jenkins（挂载点、env、依赖顺序都在 compose 里）
- 不把 `.env` 真值写进文档、注释、测试夹具
- 不改历史（重写会让 PR 引用失效、CI 缓存错位）
- 不直接推 `main`，不用 Squash 合并
- AI 不做合规判定、不做生产变更、不碰密钥真值（[AI 协作开发](../AI-协作开发.md)）

## 5. 反证要求

改断言、改门禁、改期望值，PR 里必须同时贴「改坏一处 → 红」与「恢复 → 绿」两半，
见 [质量管理计划](../project/质量管理计划.md) §3。#138 的教训是静态断言要跟随架构真源，
不要在测试里复制一份会过期的字面量。
