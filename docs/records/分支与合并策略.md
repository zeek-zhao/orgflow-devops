# 分支与合并策略

> 状态：适用 | 最后核对：2026-11-24 | 对应分支：feat/m0-v2

## 合并方向

```
main  ←  feat/m0-v2（集成分支/发布汇总）  ←  feat/m0-v3-t9/t10/t11（功能分支）
                ↑                                  ↑
          发布 PR（汇总）                    各任务 PR（feat/m0-v2 为目标）
```

- **功能分支 → feat/m0-v2**：每个任务（T9/T10/T11…）从 `feat/m0-v2` 起独立分支
  `feat/m0-v3-t<N>-<slug>`，一个 Issue + 一个 PR，PR 首行 `Closes #<issue>`。
- **feat/m0-v2 → main**：发布 PR 汇总，人工验收通过后合并；不由功能分支直推 main。
- 合并方式：**rebase 合并**（禁止 Squash，保留逐任务提交粒度与 Issue 关联）。

## 硬规则

1. **动平台 / 镜像 / 网络的功能分支，一律不得直接 push 到 `feat/m0-v2`**——必须走 PR。
2. 顶层不得出现 `docker-compose.yml`；启停一律 `./up.sh`，单服务 `--only` / `--recreate`，禁止全量 `down`。
3. 不重启整机、不重建 docker 网络、不重建数据卷；线上是长期在线 sandbox。
4. 域名走 `GATEWAY_DOMAIN` / `PUBLIC_HOST` 配置，不写死；镜像引用必须 `@sha256` 或 lock 校验通过的 `orgflow/m0-*`。
5. 每次操作写入 `docs/records/执行日志/<日期>.md`：命令 + 退出码 + 关键输出 + 结论。
