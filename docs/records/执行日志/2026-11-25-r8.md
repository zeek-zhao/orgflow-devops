## P1 — 修 up.sh 假成功
**根因（重大发现）**：`DC()` 函数只拼 `-p/-f`，未透传 `"$@"`（up/pull 子命令及选项全被丢弃），`docker compose` 打印 usage 但退出 0；叠加 `>/dev/null 2>&1` 吞错误，导致 `up.sh` 从未真正启动容器——这是 M1 r7"重建了但没重建"假成功的真正原因。

修复：
1. `DC()` 加 `shift` 并透传 `"$@"`（真正根因）。
2. `run_one` 的 pull / compose up 改为捕获输出 + `$?`，失败打印 stderr 末 15 行并 `return 1`。
3. compose up 显式 `--pull never`（拉取已由独立步骤完成），避免坏镜像在 up 阶段隐式拉取阻塞。
4. FORCE 分支重建前记录 StartedAt，重建后比对：未变判失败。

实测：
- 坏镜像（`orgflow-doesnotexist:badtag123`）ofv2 命名空间：`UP_EXIT=1`，打印 `No such image`，快速失败（不再卡 90s）。
- 正常重建 ofv2-dnsmasq：`StartedAt` 从 `15:41:44` → `15:41:59`，exit 0。
- 线上 8 容器未受影响（误删的 of-dnsmasq 已恢复）。

**须如实记录的残余风险**：物理可用仍只有约 5~5.7 GiB，Harbor 官方栈 8~9 个容器（Core/Registry/Jobservice/PostgreSQL/Redis/Trivy/Nginx/Portal）在内存紧张时会落 8 GiB swap，换页严重、性能下降，极端下仍可能 OOM。闸门绿是按含 swap 口径达成，不等于物理资源充足。M2.2 部署全程监控内存，OOM 立即回滚 registry:2。cgroup/swap 为运行时状态、重启失效，已由 `expand-memory.sh` 固化恢复入口。
