## 2. P2 — 镜像改内容哈希标识（替代 digest 回填）

**为什么**：CI 每次构建的 imageId/manifest digest 随机变化，把 digest 回填进 compose 形成「配置领先镜像」死循环。新方案用「Dockerfile + 它 COPY 的真源文件」的内容哈希做标识：输入不变→哈希恒定；输入变→哈希变，门禁可拦。

**改造**：
- 新增 `scripts/image-hash.sh <svc>`：Dockerfile + COPY 真源（跳过 build/ 生成物）逐文件 sha256 再汇总为 64hex；`dns` 别名归一在门禁层处理。
- `scripts/check-images.sh` 重写：SERVICES/BUILDABLE 扫描 `services/*/` 派生；新增 `HASHED=(jenkins jenkins-agent)`；删 `--mode=source`；`check_digest` 对 HASHED 只要求 `imageId="-"`（M0 仍 64hex）；`check_lock` 对 HASHED 强校验 `image-hash.sh == LK_ctx` 且 `tag 后缀 == ctx-<hash:0:12>`；`check_overlay` 用 `LK_tag` 取镜像名、删 PENDING 分支。
- `tests/images.lock`：M1 两行 tag 改 `orgflow/m1-<svc>:ctx-<12>`、imageId 改 `-`、contextSha256 写主标识；dnsmasq/router/certs-init 的 upstreamDigest 统一为 `FROM` 基底 `sha256:fe815609…`（原记自建 manifest digest，口径冲突）；homepage/ldapadmin 的 `-` 补上哈希。
- 两个 jenkins compose 默认值 `@sha256:<64hex>` → `:ctx-<12>`，无 `@sha256`；`config/images.env` 同步。
- CI `build-images.yml`：删 `fill-pending` job、`workflow_dispatch.services` 输入、matrix `tag: m1-v0.1`；build job 加一步算内容 tag 供 metadata-action 使用；删除回填 artifact。
- 删除 `scripts/update-images-lock.sh`、`scripts/build-images.sh`；Makefile `images-lock` → `images-hash`，`images-guard` 改走 `--mode=lock`。
- `scripts/check-fast.sh` 的「摘要一致」改走 `--mode=lock`，使反向门禁生效。

**实测**（14 条判据相关）：
- 哈希确定性：连跑 `image-hash.sh jenkins` 3 次同值 `b4db8ffda32f…`。
- 哈希敏感度：临时改 `plugins.txt` 一行 → 哈希变；还原后恢复。
- lock 与实现一致：`check-images.sh --mode=lock` 绿，M1 2 项哈希与 tag 后缀一致。
- 反向门禁：故意在 Dockerfile 加一行 → `check-fast.sh` = 1（「摘要一致 红」）；还原后绿。
- compose 引用：两个 compose 均为 `ctx-` tag，无 `@sha256`。
- CI 无回填：`.github` + `docs/运维` grep `fill-pending` 零命中。
