# 问题解决方案记录（真机启动 + 公网暴露阶段）

> 记录从"静态门禁全绿"到"真机可运行、公网可达"过程中暴露的问题、根因、方案与验证。
> 配置标识 DOC-R-001。日期 2026-11-24。

## 背景

T0–T9 的静态门禁（`make check`/`make verify`）全部通过后，真机 `docker compose up` 与公网暴露阶段仍暴露出一系列**只有运行时才会显现**的问题。本文逐一记录，便于追溯。

## P1 · ldap 首启崩溃（阻塞整条启动链）

**现象**：`docker compose up` 顺序启动到 ldap 时失败，容器 `Exited (1)`，日志停在 `[ldap] 启动 slapd`，caddy 及后续服务因依赖未就绪全部起不来。

**根因（四个叠加 bug）**：
1. `bootstrap.ldif.tmpl` 未被 Dockerfile `COPY` 进镜像，初始化时无模板可用。
2. 初始化判断用 `[[ ! -d /etc/ldap/slapd.d/cn=config ]]`，但该目录由 apt 预置、恒存在，导致**跳过初始化**；随后 `slapd -f slapd.conf` 因文件不存在而失败。
3. 修复判断后，临时初始化用 `slapd -f ... &` 未加 `-d 0`，slapd 默认 daemonize（fork），`kill $pid` 只杀父进程，真正持有 389 端口的子进程残留，正式实例报 `bind(6) failed errno=98 (Address already in use)`。
4. slapd 后端以动态模块提供，slapd.conf 未 `moduleload back_mdb`，报 `Unrecognized database type (mdb)`。

**方案**（`services/ldap/Dockerfile` + `entrypoint.sh`）：
- Dockerfile 补 `COPY bootstrap.ldif.tmpl /etc/ldap/bootstrap.ldif.tmpl`。
- 初始化判断改为 `[[ ! -f /etc/ldap/slapd.conf ]]`（我们自己生成的标志文件）。
- 临时 slapd 加 `-d 0` 前台运行 + `wait $pid` + 轮询等 389 释放。
- slapd.conf 补 `modulepath /usr/lib/ldap`、`moduleload back_mdb`。

**验证**：容器持续 running；管理员绑定返回目录条目；匿名访问被拒。

## P2 · caddy 无法启动（缺二进制）

**现象**：caddy 容器 `Exited (127)`，日志 `exec: /usr/local/bin/entrypoint.sh: line 53: exec: caddy: not found`。

**根因**：`services/caddy/Dockerfile` 只装了 `curl/ca-certificates/openssl/bash`，**从未安装 caddy 本体**。CI 忠实构建了这个有缺陷的 Dockerfile。

**方案**：Dockerfile 改用官方 cloudsmith apt 源安装 caddy（导入 GPG key + 加源 + `apt-get install caddy`，实测 2.11.9）。

**验证**：caddy 容器 healthy，admin API `http://127.0.0.1:2019/config/` 返回 200。

---

## P3 · router 路由端点失效（缺 PyYAML）

**现象**：router 容器虽 healthy（healthcheck 只探 `/healthz`），但 `/render`、`/routes` 端点因 `import yaml` 失败返回 422。

**根因**：`services/router/Dockerfile` 只装 `python3 curl`，`server.py` 依赖 PyYAML（有 try/except 降级为 `yaml=None`，会显式报错）。

**方案**：Dockerfile 补 `python3-yaml`。

## P4 · 内网 caddy 站点反代 502（服务名写错）

**现象**：内网 `home.org-devops.local` 站点反代失败。

**根因**：entrypoint 生成的 Caddyfile 写 `reverse_proxy home:3000`，但 compose 服务名是 `homepage`（容器名 `of-homepage`），Docker DNS 里没有 `home` 这个主机名。

**方案**：改为 `reverse_proxy homepage:3000`。

## P5 · LDAP 用户配置（对齐 main，按现有服务精简）

**需求**：参考 main 分支的用户配置，只建现有服务需要的用户，多余的不建。

**分析**：main 的 `services/auth/ldif/users.ldif` 有 10 个账号（platform-admin/dev/qa、gerrit-*/nexus-*/jira-*、zeek.zhao），对应 gerrit/nexus/jira 等**本底座不存在的服务**。本底座 7 服务中唯一需要 LDAP 身份的是 ldapadmin 目录管理页。

**方案**（`bootstrap.ldif.tmpl` + `entrypoint.sh`）：
- 只保留 2 个账号：`svc-platform-admin`（平台管理员服务账号）、`zeek.zhao`（所有者），结构对齐 main 的 `inetOrgPerson + posixAccount`（uidNumber/gidNumber/homeDirectory/loginShell/mail/displayName 等字段齐全）。
- 口令用独立的 SSHA 哈希（`SVC_PASSWORD`/`OWNER_PASSWORD` 环境变量，默认复用 `LDAP_PASSWORD`），不硬编码。
- 组 `svc-platform-admin` 的 member 指向新用户 DN。

**验证中暴露的两个问题**：
1. `posixAccount` objectClass 无效（`value #2 invalid per syntax`）→ slapd.conf 补 `include /etc/ldap/schema/nis.schema`。
2. 用户口令正确却绑定报 `Invalid credentials (49)` → ACL 未给 userPassword `anonymous auth` 权限，bind 阶段（匿名身份）slapd 读不到 userPassword。修复：单列 `access to attrs=userPassword ... by anonymous auth`。

**最终验证**：两个用户均绑定成功（`ldapwhoami` 返回各自 DN）；匿名读目录被拒（result 50）；目录 6 条条目。

## P6 · 公网访问架构：从"网关直连"改为"Caddy 唯一入口"

**需求**：所有服务都经 Caddy 代理到公网，用户可通过公网直接访问所有服务（不再是本地 IP）。

**初始方案**：Funnel → 自建 Flask 式网关 `public-gateway.py`（按路径直连容器 IP）。问题：旁路网关绕过了 Caddy，且网关监听 127.0.0.1 导致 Caddy 容器无法反代到它。

**最终方案**（符合底座"唯一入口"设计）：Caddy 增加公网入口站点 `:18081`（纯 HTTP，TLS 已在 Funnel 边缘终止），按 path 反代所有服务 + 提供总览页/存活探针；Funnel 指向 `127.0.0.1:18081`。链路：公网 → Funnel → Caddy → 各服务。

**方案要点**：
- `services/caddy/entrypoint.sh` 增加公网站点块（`handle_path` 去前缀反代 + `respond` 总览页 + `/healthz`）。
- `docker-compose.yml` 与服务级 compose 给 caddy 加 `${PUBLIC_PORT:-18081}:18081` 映射与 `PUBLIC_PORT` 环境变量。
- `config/defaults.env` 加 `PUBLIC_PORT=18081`，并移除尾部多余 `EOF` 行（该文件被 `.gitignore` 的 `*.env` 忽略，已在 `.gitignore` 放行入库）。
- 停用了不再需要的 `public-gateway.py`（保留文件作诊断工具）。

**Caddyfile 语法坑**：`handle_path /x/* { reverse_proxy y:80 }` 单行块写法非法（"Unexpected next token after '{' on same line"），必须改成多行块。

**验证**：公网 6 路径（`/`、`/healthz`、`/home/`、`/ldapadmin/`、`/router/healthz`、`/caddy/config/`）全部 HTTP 200；本地 Caddy 18081 各路径同样全绿。

## P7 · GitHub git push 持续 502（网络修复）

**现象**：GitHub API（建 PR/读状态）正常，但 `git push` 持续返回 HTTP 502，持续数小时。

**诊断**：
- 沙箱出网经腾讯云 GA 代理（github.com 被解析到 `43.139.79.195`）。
- `git-upload-pack`（拉取）端点 200，`git-receive-pack`（推送）端点带 Basic auth 测试也返回 200（0.4s）。
- 差异在于 git 默认用 **HTTP/2**，curl 用 `--http1.1` 全部成功。HTTP/2 over GA 代理间歇性 502。
- credential helper（`gh auth git-credential`）在非交互环境读不到 token。

**方案**（`scripts/git-push.sh`）：强制 `http.version=HTTP/1.1` + 用 `GIT_TOKEN` 构造 Basic auth 头（禁用 credential helper）。用法：`GIT_TOKEN=<pat> bash scripts/git-push.sh origin <branch>`。已在仓库 `.git/config` 固化 `http.version=HTTP/1.1`。

**验证**：封装脚本推送成功（`Everything up-to-date`），本地与远程 HEAD 一致。

**附带**：公共 DNS（8.8.8.8/1.1.1.1）查询被沙箱限制，hosts 直连方案不可用；HTTP/1.1 是更有效的解法。
