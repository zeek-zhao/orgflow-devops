# 文档管理规范（IEEE 828 / 1016 轻量落地）

> 适用范围：`docs/` 下全部文档，以及 `README.md`、`tools/*/README.md` 这类仓库内说明。
> 实施日期：2026-11-11。门禁脚本：`scripts/check_docs_meta.py`。

## 1. 为什么要立这个规范

不是为了让文档「看起来正规」，是为了解决三件已经发生的事：

| 已经发生的事 | 代价 |
|---|---|
| `docs/` 54 篇里混着**稳定文档**（服务手册、ADR）和**过程记录**（会话交接、待办、验收记录），接手人分不清哪个能信 | 每次交接都要重新判断一遍可信度 |
| 验收脚本的期望值停在 `#86` 之前（jenkins/ldapadmin 期望 302，实际 403/200） | `make deploy` 在**正确**的环境上必然失败；执行的人也学会了忽略红灯 |
| 文档改名/移动后链接静默烂掉，公开导出后又有 11 条死链 | 读者分不清是文档错了还是自己找错了地方 |

这三件事的共同点：**没有「谁是这份文档的负责人、它现在是什么状态、什么时候该重看」的记录**。
规范只补这一层，不重写内容。

## 2. 四层信息架构

分层判据只有一个：**读者拿它干什么**。

| 层 | 前缀 | 回答的问题 | 内容 | 是否发布到公开镜像 |
|---|---|---|---|---|
| 入口 | `DOC-E-` | 我该读哪一份？ | 文档地图、索引 | ✅ |
| 规程 | `DOC-P-` | 我该怎么做？ | 派单、提交、评审、发布、命名、账号 | 部分 ✅ |
| 参考 | `DOC-R-` | 事实是什么？ | 服务手册、网络架构、ADR、设计说明、测试体系 | ✅ |
| 记录 | `DOC-L-` | 当时发生了什么？ | 会话交接、待办、验收记录、任务卡、AI 会话清单 | ❌ 一律不发布 |

判定技巧：

- **参考层**写的是「系统现在是什么样」，改它等于改事实，必须配代码/配置变更。
- **记录层**写的是「某天的状态」，**允许过期、不要求维护**，过期了也不删 —— 它是审计证据。
- 一份文档如果同时承担两种职责（例如「服务手册里夹着验收结论」），拆开：结论进记录层。

## 3. 文档标识（DOC-ID）

```
DOC-<层>-<三位序号>        入口 E / 规程 P / 参考 R / 记录 L
例外：ADR-NN（架构决策）、TC-<批次>-NN（任务卡）
```

- 编号**一经分配永不复用**，删掉的文档保留一行 `status: archived`。
- 编号与文件名解耦：文件名可以改，编号不变。这是链接能烂、追溯不能断的原因。

## 4. 生命周期

```
draft ──▶ review ──▶ approved ──▶ superseded ──▶ archived
  ▲          │            │
  └──────────┘            └──▶ (内容过时但结论仍有效) ──▶ archived
```

每个状态的**准入门槛**（门禁脚本会查）：

| 状态 | 含义 | 硬性要求 |
|---|---|---|
| `draft` | 还在写，**不可作为依据** | 无 |
| `review` | 待评审 | 责任人已指定 |
| `approved` | 可作为依据 | **必须有评审日期**（YYYY-MM-DD） |
| `superseded` | 被新文档取代 | **必须用 `→` 指向替代者** |
| `archived` | 不再维护，仅存档 | 不参与复审超期检查 |

状态是自我声明。**没有见证字段的状态等于没有状态** —— 这正是「验收脚本期望过期却没人发现」的成因：
脚本里没有「这条期望对应哪次架构变更」的字段，所以 `#86` 改了架构，脚本不知道。

## 5. 评审

- **谁能改**：任何 PR 都可以改文档；改 `approved` 文档的**结论部分**必须有对应 Issue 或代码变更。
- **评审判据**（按层不同）：

| 层 | 评审看什么 |
|---|---|
| 入口 | 新文档是否被索引、链接是否可达 |
| 规程 | 步骤能否照着做出来、失败时怎么判断 |
| 参考 | 与 `docker-compose.yml`/`config/` 是否一致、命令是否实测过 |
| 记录 | 不评审内容，只评审「是否标注了日期与结论」 |

- **复审周期**写在登记册的 `复审(月)` 列。超期只 WARN 不阻断：**文档不会因为到期就变错**，
  但需要有人看一眼决定「续期 / 改 / 退役」。

## 6. 变更控制

1. 改文档跟改代码同一条 PR，不单独开「文档整理 PR」—— 那样评审时没人知道结论对不对。
2. 改 `approved` 文档的结论 → PR 描述必须写「依据」（Issue 号 / 实测命令输出）。
3. 文档改名/移动 → 同 PR 内跑 `make test`（`scripts/test_docs.py` 查相对链接）。
4. 架构性变更 → 先写 ADR，再改服务手册，最后改入口索引。顺序反了就会出现「手册比 ADR 新」的矛盾态。

## 7. 追溯

一条需求的完整证据链：

```
需求（Issue）→ 设计（ADR / 设计说明）→ 任务（task-cards）→ 验收（验收记录）→ 代码（PR）
```

文档侧只需保证**四段都有指针**：

- 需求：登记册 `关联` 列写 Issue 号。
- 设计：ADR 头部写「因何而起」（Issue 号）。
- 任务：任务卡头部写需求号（现有 `REQ-M0-xx` 编号即此）。
- 验收：验收记录写 commit 与实测输出，不写「已验证」三个字。

## 8. 审计

| 频率 | 动作 | 产出 |
|---|---|---|
| 每次 PR | `make test`（含 `check_docs_meta.py`） | CI 红灯即阻断 |
| 每月 | 看 WARN 列表决定续期/退役 | 登记册更新 |
| 每次对外发布 | 跑脱敏门禁 + 死链检查 | 见 `docs/使用说明.md` |

## 9. 退役

- 内容过时但结论仍有效的：`archived`，**不删**。
- 有替代者的：`superseded` + `→`，保留 3 个月后转 `archived`。
- 从未被引用的草稿：直接删除，登记册同步删行（这是唯一允许删除登记项的情况）。

## 10. 条款映射

| 标准条款 | 本规范的落点 |
|---|---|
| IEEE 828 §配置标识 | DOC-ID（§3）+ 登记册 |
| IEEE 828 §配置控制 | 变更控制（§6）+ PR 绑定 |
| IEEE 828 §状态纪实 | 生命周期（§4）+ 登记册状态列 |
| IEEE 828 §配置审计 | 门禁脚本（§8，硬查 5 类、软查 1 类） |
| IEEE 1016 §设计描述结构 | `docs/_templates/设计说明.md`（上下文/组成/交互/数据/资源/决策理由） |
| IEEE 1016 §设计视图 | `docs/M0-最小核心.md` 的「组件 + 交互」两节即该视图的最小实现 |
